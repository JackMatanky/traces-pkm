# 09 — Task-Level Queries

**What to build:** Task-level queries operate on individual tasks instead of pages. The CLI and Template surfaces can query tasks while preserving task status and parent Note metadata.

**Blocked by:** 03 — Dataview Inline Fields, Tags, and Frontmatter Key-Value Parsing, 05 — QueryOutcome Filtering and Ordering

**Status:** completed

- [x] Task-level QueryOutcome values represent individual tasks.
- [x] Task records expose completion status and task text.
- [x] Task records retain parent Note metadata for filtering and display.
- [x] `traces task` runs task-level queries and prints task output.
- [x] Templates can use a task-level query source.
- [x] Task query tests prove task-level filtering does not operate on page rows by mistake.

### Implementation Notes

- **`IndexRecord` reused for task rows, not a new `TaskRecord` type**
  (`src/index/query.rs`): a task row is an `IndexRecord` with a new
  `task: Option<TaskInfo>` field set via `IndexRecord::with_task`. This
  reuses the entire existing `QueryOutcome`/`IndexRecord` machinery
  (`filter`/`where`/`sort`/`limit`/`group_by`/`flatten`, and the minijinja
  `Object` impls from #06) for tasks with zero duplication, and gives task
  rows the parent Note's `file.*`/frontmatter/inline-field/tag metadata for
  free via the existing `IndexRecord::field` resolver — directly satisfying
  "Task records retain parent Note metadata for filtering and display."
  `task: None` on page-level records.
- **`task.<field>` accessors** (`FieldPath::Task(TaskField)`, mirroring the
  existing `file.<field>` prefix handling exactly): `task.completed` (bool)
  and `task.text` (string). Resolve to `Null` on page-level records — the
  same "well-formed path, no value" contract every other field already
  documents.
- **`FileIndex::query_tasks`** (`src/index/mod.rs`): selects the same Notes
  `FileIndex::query` would (via `Source::is_match`, shared through a new
  `matched_pairs` helper extracted from both), then expands each matched
  Note into one `IndexRecord` per `Note::tasks()` item instead of one
  record per Note. `query()` was refactored onto the same `matched_pairs`
  helper to remove the duplicated merge-join it previously inlined.
- **`traces task` CLI** (`src/cli/task.rs`, new): `--from <#tag|folder>`
  (omitted = every task) and `--where <expr>` flags, refreshes the
  `FileIndex`, prints one markdown checkbox line per task to stdout,
  diagnostics to stderr. `Task::lines()` is split out from `Task::run()` so
  tests assert on rendered content without capturing process stdout.
  `CliError::Query` added for `--where` filter-parse failures, mirroring
  the existing `CliError::Index` pattern.
- **`tasks` template namespace** (`src/template/engine/query_ops.rs`):
  `TaskOps` mirrors `QueryOps` exactly (`all()`/`from_tags()`/
  `from_folder()`, same trusted-root plumbing) but calls
  `FileIndex::query_tasks` instead of `FileIndex::query`. `record.task.*`
  resolves through a `TaskFields` wrapper mirroring `FileFields`, needed
  because minijinja resolves a dotted attribute path one segment at a
  time. Registered as the `tasks` global in `TemplateEngine::new` alongside
  `query`.
- **Task-row-not-page-row test coverage** (satisfying the ticket's own
  acceptance criterion 6): tests at every layer prove a two-task Note
  produces two task rows (not one page row), and that `.filter()`/`.where()`
  on a task field keeps only the matching task row rather than the whole
  Note — `src/index/mod.rs`'s
  `expands_one_note_with_two_tasks_into_two_rows_not_one` and
  `filtering_by_task_completion_keeps_only_matching_tasks_not_the_whole_note`,
  mirrored at the CLI (`src/cli/task.rs`) and template
  (`src/template/engine/query_ops.rs`) seams.
- **Verification**: `mise run fmt`, `mise run clippy` (`-D warnings`),
  `cargo clippy --workspace --tests --all-features -- -D warnings` (three
  pre-existing unrelated lint failures in `src/index/query/error.rs`'s
  test module and one large-stack-array error confirmed present on `main`
