## Agent Brief

**Category:** enhancement
**Summary:** Register a `query` minijinja namespace Object so templates can build and consume FileIndex queries via method chaining.

**Current behavior:**
The FileIndex query machinery (`FileIndex::refresh`, `FileIndex::query`, `Source`, `QueryOutcome`, `IndexRecord`, and `QueryOutcome`'s `where`/`filter`/`sort`/`limit`/`group_by`/`flatten` transformations) exists and is fully covered by unit tests, but nothing outside those tests calls it. `TemplateEngine`/`TemplateService` currently register `file`, `ui`, and `date` as minijinja namespace Objects — each backed by a small struct implementing minijinja's `Object` trait (method dispatch via `get_value`/`call_method`) and registered with `env.add_global(name, Value::from_object(self))`. There is no `query` namespace, and no wiring anywhere from a trusted project root into a `FileIndex` for a render to query against. `QueryOutcome`/`IndexRecord` are plain Rust types today — neither converts to a minijinja `Value`, so neither can be iterated, indexed, or passed to `ui.select`/`ui.multi_select` yet.

**Desired behavior:**
Templates gain a `query` namespace Object, registered the same way as `file`/`ui`/`date`. Its methods mirror the FileIndex's existing `Source` selection — all Notes, a tag source, a folder source — and return a `QueryOutcome` that is now a minijinja `Value`:
- Iterable with `{% for %}`.
- Indexable by integer position.
- Exposes a length.
- Chains further `QueryOutcome` methods (`.where(...)`, `.filter(...)`, `.sort(...)`, `.limit(...)`, `.group_by(...)`, `.flatten(...)` — already implemented in Rust) via minijinja `call_method`.
- Each yielded item (`IndexRecord`) exposes `file.*`, frontmatter, inline-field, and `tags` attributes to minijinja — reuse the existing `IndexRecord` field resolver as the attribute backend rather than building a second lookup path.

`ui.select`/`ui.multi_select` already accept any iterable `Value` and derive display labels through an `attribute=` kwarg path-walk. Once `QueryOutcome`/`IndexRecord` convert to `Value` correctly, passing a `QueryOutcome` to either should need no changes to that code — demonstrate it rather than special-casing query results there.

Before a template can query anything, `TemplateEngine`/`TemplateService` construction needs a route to a `FileIndex` for the render's project root, refreshed lazily before the query executes (per ADR-0005 and #04's `FileIndex::refresh`), reachable by the `query` namespace Object. This wiring doesn't exist yet anywhere in `TemplateService`/`TemplateEngine` and is this ticket's to design.

Query failures (unknown field path, malformed filter/sort/limit input — `QueryError`'s existing variants) must surface as minijinja `Error`s carrying template name, line, and column, the same way other fallible namespace methods already convert their domain errors — not panics, not silently-empty results.

**Key interfaces:**
- A `query` namespace Object registered like `FileOps`/`UiOps`/`DateOps`, holding whatever the render needs to reach a fresh `FileIndex` for the project root.
- `QueryOutcome`/`IndexRecord` minijinja `Value`/`Object` conversions: iteration, indexing, length, and (for `IndexRecord`) attribute resolution via the existing field resolver.
- A `QueryError` → `minijinja::Error` conversion carrying render context.
- `TemplateEngine`/`TemplateService` construction gaining a route from a trusted project root to a lazily-refreshed `FileIndex`.

**Acceptance criteria:**
- [ ] The minijinja environment exposes a `query` namespace Object.
- [ ] `query`'s methods mirror the FileIndex's `Source` selection (all Notes, by tag, by folder) and return `QueryOutcome` values.
- [ ] `QueryOutcome`'s existing transformation methods (`where`/`filter`, `sort`, `limit`, `group_by`, `flatten`) are callable via method chaining directly on the value a `query` method returns.
- [ ] Templates can iterate a `QueryOutcome` with `{% for %}`, yielding items whose `file.*`, frontmatter, inline-field, and `tags` attributes resolve correctly.
- [ ] Templates can index into a `QueryOutcome` by integer position.
- [ ] Templates can read a `QueryOutcome`'s length.
- [ ] A `QueryOutcome` can be passed directly to `ui.select` and `ui.multi_select`, with `attribute=` deriving a display label from a field on each item.
- [ ] Query method failures (unknown field path, malformed filter/sort/limit input) surface as minijinja render errors carrying template name, line, and column — not panics.
- [ ] The FileIndex is refreshed before a template's query executes, so results reflect the current project root.

**Out of scope:**
- Terminal renderers (`table`, `list`, `task_list`, `count`) and their pipeline-filter equivalents — belongs to #07.
- Task-level queries (`tasks.*` namespace) — belongs to #09.
- CLI query commands (`traces list`/`table`/`task`) — belongs to #08.
- Changing `QueryOutcome`'s transformation logic itself — already implemented in #05.
- A Dataview Query Language parser or DataviewJS.
