## Agent Brief

**Category:** enhancement
**Summary:** Add a redb-backed FileIndex that `traces index` builds and persists, storing a File Record for every file under a trusted project root with `created_at`/`modified_at`/`size` freshness metadata.

**Current behavior:**
Traces has no index. `traces` exposes `init`, `trust`, `template`, and `completions` subcommands (see the top-level `Commands` enum and its dispatch), plus the default `-i` template dispatch. Trust and project-root resolution already exist via the config service and trust plumbing. Nothing scans the project root or persists file metadata, so Templates and CLI commands cannot query the project as a knowledge base. `redb` is not yet a dependency.

**Desired behavior:**
A trusted project can run `traces index` to scan every file under its project root and persist a FileIndex to disk. Each indexed file gets a File Record carrying its path, name, folder, created time, modified time, and size. The persisted FileIndex survives across process invocations: a later command loads it rather than rescanning from scratch. Freshness is expressed purely in terms of `(created_at, modified_at, size)` so later tickets can detect stale entries cheaply. Running `traces index` again rebuilds/refreshes the index. This is the foundation slice — richer Note Metadata (frontmatter, inline fields, tags, tasks, lists, links), lazy refresh on query, and the query surface are separate downstream tickets.

**Key interfaces:**
- A `FileIndex` type behind a deep interface: build-from-root, persist, load, and enumerate File Records. Callers (CLI, later Templates) must not see redb table details — persistence is an internal concern per ADR-0005 and the spec's Further Notes.
- A `File Record` value exposing `file.path`, `file.name`, `file.folder`, `file.created_at`, `file.modified_at`, and `file.size`. (Dataview-style `ctime`/`cdate`/`mtime`/`mdate` accessors are specified but may land here or in the metadata ticket; at minimum the underlying timestamps/size must be stored.)
- Persistence uses `redb` (new dependency). ADR-0005 mandates two tables keyed by path — one for File Records, one for Note Metadata; this ticket only needs the File Record table, but the schema should not preclude adding the Note Metadata table.
- A new `Index` variant on the top-level `Commands` enum, wired through the same parsed-argv dispatch path as the existing subcommands, resolving the trusted project root through the existing config/trust service.

**Acceptance criteria:**
- [ ] `traces index` builds a persisted FileIndex for a trusted project root.
- [ ] Every indexed file has a File Record with path, name, folder, created time, modified time, and size.
- [ ] The persisted FileIndex can be loaded in a later command invocation without rescanning.
- [ ] Freshness metadata is stored in terms of `created_at`, `modified_at`, and `size`.
- [ ] Tests cover the FileIndex through its public interface (build, persist, reload) and the CLI through command dispatch on an isolated trusted project root; redb persistence is verified via observable reload behavior, not by inspecting redb internals.

**Out of scope:**
- Note Metadata extraction (frontmatter, inline fields, tags, tasks, lists, links) — ticket 02/03.
- Lazy refresh of stale entries during query execution — ticket 04.
- Any QueryOps namespace, QueryOutcome, or CLI query commands (`list`/`table`/`task`) — later tickets.
- Content hashing for freshness — the spec mandates `(created_at, modified_at, size)`, not blake3.
- A background file watcher/daemon and JSON output.
