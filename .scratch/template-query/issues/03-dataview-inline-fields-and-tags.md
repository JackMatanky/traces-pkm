# 03 — Dataview Inline Fields and Tags

**What to build:** Markdown Notes index Dataview-compatible Inline Fields and markdown tags from body text and list items. Inline Fields remain in the Note source, but they do not index inside fenced code blocks, indented code blocks, or inline code.

**Blocked by:** 02 — Markdown Note Metadata Extraction

**Status:** ready-for-agent

- [x] `Key:: Value` body fields are indexed as Inline Fields.
- [x] `[Key:: Value]` inline fields are indexed as visible-key Inline Fields.
- [x] `(Key:: Value)` inline fields are indexed as hidden-key Inline Fields.
- [x] Inline Fields in list items are indexed.
- [x] Inline Fields inside fenced code blocks, indented code blocks, and inline code are ignored.
- [x] Markdown tags are indexed for tag source queries.

### Implementation Notes

- **Module Architecture**: new `src/index/markdown/inline.rs` submodule
  houses the Inline Field/tag lexer (`extract_inline_fields`,
  `extract_tags`), kept separate from `parser.rs`'s `pulldown-cmark` event
  walk and `types.rs`'s domain model, mirroring #02's
  types/parser split.
- **Domain Types (`types.rs`)**:
  - `InlineFieldForm`: `Body` | `VisibleKey` | `HiddenKey`.
  - `InlineField`: `key: String`, `value: String`, `form: InlineFieldForm`.
  - `Note` gained `inline_fields: Vec<InlineField>` and `tags: Vec<String>`
    (tags keep their leading `#`). `Note::new`'s arity was **not** grown to
    7 params (`clippy::too_many_arguments`/`max-struct-bools` risk aside,
    7 params was already the wrong shape) — instead `Note::with_inline_fields`
    and `Note::with_tags` are consuming builder methods chained onto
    `Note::new`, matching the existing `ListItem::with_children` builder
    naming precedent.
- **Design deviation from the Agent Brief's stated key interface** —
  *"`CodeRegion` ranges from #02 are the exclusion source for fenced code,
  indented code, and inline code."* The implementation does **not**
  subtract `CodeRegion` byte ranges from raw source in a second pass.
  Instead, `ParserContext` (in the *same* single event-stream pass that
  already produces `CodeRegion` entries) composes two new plain-text scan
  buffers — one per top-level body paragraph (`body_buffer`), one per list
  item (`ItemFrame::scan_buffer`) — that skip fenced/indented code block
  text and inline code as they're built, via the same `BlockContext`
  state transitions that produce `code_regions`. The lexer then runs only
  over these pre-excluded buffers. This observes the identical exclusion
  boundaries as `CodeRegion` would, without a second raw-source regex pass
  or byte-range overlap arithmetic — cheaper and simpler than deriving
  exclusions from stored ranges after the fact. `Note::code_regions()`
  itself is unchanged and still exposed (kept for #02's own contract; nothing
  in #03 needed to add a second consumer of it).
- **Parsing (`parser.rs`)**:
  - Replaced three independent `bool` flags (`in_metadata_block` from #02,
    plus two new ones this ticket would have added) with one
    `BlockContext` enum (`None | MetadataBlock | CodeBlock | Paragraph`) —
    the three states are mutually exclusive at the top-level-block
    granularity, and `clippy.toml`'s `max-struct-bools = 2` would have
    denied a third bool on `ParserContext` (`clippy::struct_excessive_bools`
    is a deny-level lint here).
  - New `Tag::Paragraph`/`TagEnd::Paragraph` handlers
    (`start_paragraph`/`end_paragraph`) gate `body_buffer` accumulation —
    scoped to top-level paragraphs, not headings/blockquote-direct text,
    a deliberate scope call (see Known Limitations).
  - `ItemFrame` gained `scan_buffer: String`, populated in lockstep with
    the existing `text_buffer` by `push_text`/`push_break`, except it never
    receives inline-code text (unlike `text_buffer`, whose #02 behavior of
    including inline-code content in `ListItem::text()` is preserved
    unchanged) and is skipped while `BlockContext::CodeBlock` is active.
  - `end_item`/`end_paragraph` lex their buffer and extend
    `ParserContext::inline_fields`/`tags` before the buffer is
    cleared/consumed — the single event pass yields Inline Fields/tags in
    overall document order for free (no separate sort-by-position pass at
    the `Note` level was needed).
- **Lexing (`inline.rs`)**: four `LazyLock<Regex>` statics — bare
  `Key:: Value` requires a single-word key (no spaces; letters/digits/`_`/`-`
  only) since it's unbounded on a line and a multi-word key would swallow
  entire sentences containing `::` (bracket/paren forms allow multi-word
  keys since they're delimiter-bounded). Tag matching separates "find a
  `#word` token" (`TAG_RE`, no lookaround) from "is it preceded by a
  non-alphanumeric boundary" (checked directly against unconsumed `text`
  in `extract_tags`) rather than folding the boundary into a consuming
  regex alternative, which the `regex` crate's lack of lookbehind would
  otherwise force and which risks losing matches to a previous match's
  own consumed boundary character.
- **Testing**: 733 tests pass (733 lib+bin+integration+doctests total;
  53 in `index::markdown::*` alone), `cargo clippy --all-targets
  --all-features` clean (only a pre-existing unrelated warning on
  `cli::run` remains, verified present on `main` too), `cargo fmt --check`
  clean.
- **Acceptance Criteria Verification** (re-checked against final code
  state):
  - Bare/visible-key/hidden-key body forms —
    `markdown::parser::tests::inline_metadata::extracts_a_bare_body_field`,
    `extracts_a_visible_key_field_from_body_text`,
    `extracts_a_hidden_key_field_from_body_text`; unit-level coverage in
    `markdown::inline::tests::inline_fields::*`.
  - List item fields —
    `extracts_a_bare_field_from_a_list_item_and_keeps_it_in_item_text`.
  - Code-region exclusion (fenced/indented/inline, both fields and tags)
    — `ignores_fields_inside_excluded_code_regions` and
    `ignores_tags_inside_excluded_code_regions` (`rstest` cases for all
    three code contexts).
  - Tags — `extracts_a_tag_from_body_text`,
    `extracts_a_tag_from_a_list_item_and_keeps_it_in_item_text`; boundary
    hardening in `markdown::inline::tests::tags::*`
    (`extracts_adjacent_tags_separated_only_by_punctuation`,
    `rejects_a_second_tag_glued_directly_onto_the_first`).
  - Fields/tags remain in enclosing plain text — the same list-item tests
    above assert `item.text()` is unchanged (e.g. still
    `"Status:: Draft #urgent"`), matching #02's link-in-item-text
    precedent; body text was never stored as a `Note` field either before
    or after this ticket, so there's no body accessor to assert against —
    the guarantee there reduces to "the source file itself is never
    rewritten," which holds trivially since nothing in this ticket writes
    to note source files.
  - FileIndex round-trip —
    `index::tests::persistence::persist_then_load_recovers_inline_fields_and_tags`.
  - Parser tests at the markdown event seam covering body text, list
    items, fenced code, indented code, inline code — all of
    `markdown::parser::tests::inline_metadata::*` (9 tests/cases).
  - **All 6 top-level and all 9 Agent Brief acceptance criteria are fully
    met.** None are partially fulfilled or outstanding.
- **Known Limitations (not AC gaps)**:
  - Body-level Inline Field/tag scanning is scoped to `Tag::Paragraph`
    content only — heading text and any direct (non-paragraph-wrapped)
    blockquote text are not scanned. No AC or spec line asks for headings;
    "normal body text" was read as paragraph prose, which is also where
    real Dataview inline fields conventionally live.
  - Bare `Key:: Value` keys are restricted to a single word (no internal
    spaces) to avoid a whole prose sentence containing `::` being
    mis-captured as one giant key. `[Key:: Value]`/`(Key:: Value)` keys
    may contain spaces since the delimiters bound them unambiguously. Not
    a stated AC, but worth flagging for #04/#06 if multi-word bare keys
    turn out to matter for real note content.
  - Tags are stored as an occurrence list, not deduplicated per `Note`
    (a Note mentioning `#book` three times gets three `"#book"` entries).
    `from_tags` (ticket #04, out of scope here) will need to dedupe or
    treat membership-only when it consumes `Note::tags()`.


## Agent Brief

**Category:** enhancement
**Summary:** Add Dataview-compatible Inline Fields and markdown body tags to Note Metadata after the Note parser from #02 lands.

**Current behavior:**
`Note` metadata from #02 covers frontmatter, lists/tasks, outlinks, and code-region ranges. It does not yet store body Inline Fields or markdown tags. Codebase redundancy check found no existing `InlineField`, `inline_fields`, markdown tag, or `from_tags` implementation in the main source tree or the active #02 worktree; only the spec/ticket text mentions these concepts.

**Desired behavior:**
Markdown Notes should index Inline Fields from normal body text and list item text while leaving the original note source unchanged. Supported Inline Field forms are:

- `Key:: Value` for body fields.
- `[Key:: Value]` for visible-key inline fields.
- `(Key:: Value)` for hidden-key inline fields.

Inline Fields must not be indexed when their source bytes are inside fenced code blocks, indented code blocks, or inline code spans. Markdown tags in body text and list items should also be indexed as Note Metadata so later tag-source queries can select Notes by tags such as `#book` and `#projects/active`.

**Key interfaces:**
- `Note` should expose stored Inline Fields and tags through small accessors; callers should not inspect parser internals or redb tables.
- `InlineField` should preserve at least key, value, and whether the syntax used body, visible-key, or hidden-key form.
- `CodeRegion` ranges from #02 are the exclusion source for fenced code, indented code, and inline code.
- The FileIndex persistence boundary should round-trip the new Note Metadata fields through the existing Note table.

**Acceptance criteria:**
- [x] `Key:: Value` in normal body text is indexed as an Inline Field.
- [x] `[Key:: Value]` is indexed as a visible-key Inline Field.
- [x] `(Key:: Value)` is indexed as a hidden-key Inline Field.
- [x] Inline Fields in markdown list items are indexed.
- [x] Inline Fields inside fenced code blocks, indented code blocks, and inline code spans are ignored.
- [x] Markdown tags in body text and list items are indexed as tags on the Note.
- [x] Inline Fields and tags remain in the plain text of their enclosing body/list item component, matching links remaining in list item text.
- [x] Inline Fields and tags survive FileIndex build, persist, and load round-trips.
- [x] Parser tests cover the markdown event seam and include body text, list items, fenced code, indented code, and inline code cases.

**Out of scope:**
- YAML frontmatter extraction, list/task extraction, outlinks, and `Note::tasks()` from #02.
- Query source selection such as `query.from_tags(...)` from #04.
- Inlinks.
- A Dataview Query Language parser or DataviewJS.
- Stripping or rewriting Inline Fields in source markdown.
