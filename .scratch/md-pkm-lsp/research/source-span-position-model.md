## Executive summary

Traces' existing architecture is a **better starting point for span-aware LSP work than the ticket's framing suggested**: `pulldown-cmark` is already invoked via `into_offset_iter()` (`src/note/parser.rs:104`), which hands every event a full `Range<usize>` — but only `range.start` is kept, cast to a `ByteOffset`, and used for exactly one purpose (list-item line tracking, `src/note/parser.rs:380-382`). The raw byte-range data for links, tags, headings, and inline fields is available at parse time today and is discarded, not absent by parser limitation. This is a materially easier fix than switching parsers.

Three genuinely separate architectural questions hide inside "source span model," and they should not be conflated:
1. **Should the `Note` AST carry spans structurally?** Yes — extend existing types, do not build a parallel span index (see Recommendations).
2. **Should the underlying parser change (pulldown-cmark → tree-sitter-markdown or another)?** No — zero precedent among every studied PKM-LSP peer (Markdown Oxide, Marksman, zk) or generic-Markdown baseline (Microsoft's service) for tree-sitter-markdown, and its own ecosystem positioning in 2026 is "editor highlighting/folding," explicitly *not* recommended where parsing correctness matters (web-verified, see Crate evaluation) — a real risk for a tool with custom inline-field/task-marker syntax layered on CommonMark.
3. **Should Traces adopt an incremental/rope-based live-buffer model?** Partially — a rope (`ropey`) is justified for the *live open-buffer* text representation (cheap edits, native UTF-16 conversion), but **full re-parse per edit on top of that rope is still correct and sufficient** — every mature PKM LSP studied (Marksman, Markdown Oxide) does full re-parse per edit, and rust-analyzer's own "parsing must never fail" partial-tree invariant is the thing that actually matters for responsiveness, not parser-level incrementality.

None of this requires abandoning `pulldown-cmark`, redb, or the existing `Note`/`FileIndex` module boundary. It requires: (a) stop discarding `range.end`, (b) widen `ByteTracker` from `pub(super)` to crate-public and extend it for UTF-16 conversion, (c) add `Range<ByteOffset>` fields to `Link`, `Tag`, inline-field entries, and a new `Heading` AST node, (d) decide frontmatter spans separately (yaml_serde has **no** per-value span capability — confirmed below — so frontmatter needs its own raw-text re-scan, not a YAML-crate feature), (e) keep spans **transient** (computed from source text at LSP-request time), not persisted in redb — persisting them is a real, avoidable index-format/migration cost for data the LSP can always recompute from the file it just re-read.

## First-principles source model analysis

For a Markdown/PKM LSP the **minimal-but-complete** model has three distinct layers, each with a different lifetime and different consumer, and conflating them is the single biggest architectural risk:

1. **Parse-time byte spans** (`Range<ByteOffset>`, UTF-8 bytes) — attached to AST nodes (`Link`, `Tag`, inline fields, headings) at parse time, from data the parser (`pulldown-cmark`, the `logos` lexer) already produces. Lifetime: as long as the parsed `Note` is held in memory. Consumer: everything that needs "where in this file is this thing" for a request against an already-open/already-read file (hover, go-to-definition target resolution, diagnostics-with-labels, rename-target discovery).
2. **A byte↔line(↔UTF-16-column) line index** — one per document, built once from the raw source string (already exists as `ByteTracker`, just needs wider visibility + UTF-16 extension). Lifetime: as long as the source text it was built from is held. Consumer: converting layer-1 byte spans into whatever the LSP wire actually needs (`lsp_types::Range`, UTF-16 by default, UTF-8 if negotiated — see next section).
3. **LSP-wire `Range`** (the negotiated encoding) — computed on demand from (1)+(2) at the point a response is serialized. Never stored; recomputed per-request. This is the only layer that needs to know about the LSP protocol at all — layers 1 and 2 stay protocol-agnostic, matching the map's standing constraint ("LSP protocol DTOs... never define core semantics").

Memory impact at scale: a `Range<ByteOffset>` is 2×`usize` = 16 bytes (or 2×`u32` = 8 bytes if byte offsets are capped at 4 GiB per file, which is a safe assumption for Markdown notes). At 50k notes averaging, say, 20 span-bearing entities each (links + tags + fields — a plausible PKM-vault estimate, not measured), that's 1M spans × 16 bytes = 16 MB **if held in memory for every note simultaneously** — the actual number is far smaller if spans are only materialized for the currently-open/currently-queried note(s) rather than the whole vault (see Persistence section: this is the strongest argument for *not* persisting spans in `FileIndex`).

Stable node IDs: **not needed as a separate concept for this ticket.** Traces' domain identity for a note is already its path (confirmed throughout `FileIndex`/`FileEntry`); identity for a link/tag/field within a note is positional (its span *is* its identity within one parse). rust-analyzer's `FileId`-as-opaque-ID pattern (External precedent, below) is about *files*, not sub-file nodes, and Traces already has the file-level equivalent.

## LSP protocol position/range requirements

Verified against the primary specification (`microsoft.github.io/language-server-protocol/specifications/lsp/3.17`, cross-checked against `docs.rs/lsp-types` and independent practitioner sources — the local `docs/refs/lsp_spec.md` copy is confirmed to be an unresolved Jekyll include-skeleton for at least the file-watching fragment, per a prior ticket's finding, so this was verified against the live spec rather than trusted from the local copy):

- **Default encoding is UTF-16 code units**, for backward compatibility with the original TypeScript/VS Code implementation. A server that says nothing about encoding **must** use UTF-16.
- **LSP 3.17 added negotiation**: client advertises `general.positionEncodings: PositionEncodingKind[]` (an ordered-by-preference list of `"utf-8" | "utf-16" | "utf-32"`) in `InitializeParams`. Server picks one and returns it in `InitializeResult.capabilities.positionEncoding`. If the server omits this field, UTF-16 is assumed regardless of what the client advertised.
- **Not every client negotiates.** Microsoft's own `vscode-markdown-languageservice`/`-languageserver` — the canonical generic-Markdown baseline already researched (ticket 05) — uses plain `vscode-languageserver-textdocument` with **no `positionEncoding` opt-in at all** (`research/ms-markdown-language-service.md:37`). This is real evidence a UTF-8-first design must still correctly and cheaply serve UTF-16 to non-negotiating clients, not treat it as a legacy edge case.
- Every range-bearing LSP feature Traces will implement (diagnostics, document links, hover, definition/references/rename ranges, folding, selection ranges, `WorkspaceEdit` text edits, semantic tokens if adopted) consumes the *same* `Range` type — there is exactly one position representation to get right, not per-feature variants.

Given `ByteOffset` is already the crate's native currency (`src/position.rs`, `pulldown-cmark`'s own offsets, `miette::SourceSpan`), the correct design is: **keep everything internal in UTF-8 bytes; convert to the negotiated encoding only at the LSP-response boundary**, using the line index (layer 2 above) extended with `ropey`'s `char_to_utf16_cu`/`byte_to_char` style conversions (confirmed available on `ropey::Rope` — see Crate evaluation) or an equivalent hand-rolled conversion over the same line-start table `ByteTracker` already precomputes. This avoids the "repeated conversion cost" the ticket asked about: convert once per response, not per internal operation, and skip the conversion path entirely for the (increasingly common, per 2026 practitioner sources) client that negotiates UTF-8.

## Existing parser/AST/index fit-gap analysis

**Sufficient as-is**: `src/position.rs`'s `SourceLine`/`ByteOffset` vocabulary — extend it (add a `Span`/`Range<ByteOffset>` type, widen `ByteOffset` to `pub`), don't replace it. `miette::SourceSpan` as the diagnostic-label shape — already proven for queries, directly reusable for Note-parse diagnostics.

**Insufficient, needs extension (not a rewrite)**: `Link`, `Tag`, `NoteFieldValue`, `ListItemPosition` all need a span field added. This is additive — every existing consumer that doesn't care about spans keeps compiling unchanged (assuming the span field isn't required for construction in test helpers, or those helpers get a small span-defaulting convenience constructor). `ByteTracker` needs its visibility widened from `pub(super)` and a UTF-16 conversion method added — no algorithmic change to what exists.

**Actively missing, needs new AST surface**: a `Heading` node. Headings are structurally significant for symbols/folding/selection-ranges/heading-anchor-links regardless of the span question, and are currently invisible to the parser except as a text-scan target for tags/fields inside them. This is a real, load-bearing gap this research surfaces that the ticket's own wording didn't name explicitly — **ticket 11's wording should be sharpened to include "does the Note AST need a first-class Heading node" as an explicit sub-question**, not left implicit inside "spans."

**Actively wrong for LSP use, would produce an awkward retrofit if merely extended**: frontmatter's `yaml_serde::Value`-based parsing. There is no clean way to bolt spans onto `serde_yaml`-family `Value` after the fact — its `Value` type carries no location for successfully-parsed content (confirmed: `yaml_serde::error::Location` exists but is scoped to `yaml_serde::error`, used only when parsing *fails*, not attached to any successfully-produced `Value` node — verified directly via `rust-docs-mcp` on the crate actually pinned in `Cargo.lock`, `yaml_serde 0.10.4`). The clean fix is not "extend `Frontmatter`," it's "add a small, purpose-built raw-text scanner that walks `RawFrontmatter`'s preserved text independently of the YAML value parse," mapping each top-level (and, if needed, nested) key to its source line/byte range by scanning for `key:` patterns — cheap, because Traces' frontmatter is flat-to-shallow key-value YAML in practice, not arbitrary deeply-nested YAML requiring a full spanned grammar.

## Parser/text-buffer/persistence alternatives

**Parser**: stay on `pulldown-cmark` + the custom `logos` lexer. The single strongest piece of evidence against switching is precedent-shaped, not opinion: **zero** studied tool — not Markdown Oxide (regex, no AST at all), not Marksman (Markdig, full re-parse per edit), not Microsoft's own canonical Markdown language service (markdown-it tokens) — uses tree-sitter-markdown for a PKM or generic-Markdown LSP, despite tree-sitter's incremental-parsing pitch being exactly what a naive analysis would reach for first. Corroborated externally (web-verified, 2026): tree-sitter-markdown's own ecosystem positioning is "production-ready for syntax highlighting/editor integration," explicitly **not recommended where absolute parsing correctness matters** (CMS/SSG-grade correctness) — and Traces' custom syntax (inline fields, task-marker shorthands, wikilinks) layered on CommonMark is exactly the kind of "complex, context-dependent" extension the same sources flag as tree-sitter-markdown's weak spot. `pulldown-cmark` is independently confirmed (its own docs, `pulldown-cmark.github.io`) as "the industry standard in Rust" for CommonMark-compliant, high-performance parsing — reversing course on it would trade a working, already-integrated, already-spec-compliant parser for a worse-fit tool, on a hypothesis ("incremental parsing helps") that every actual peer LSP examined rejected in practice by choosing full-reparse instead.

**Text buffer / rope**: adopt `ropey` — but scoped correctly. Its `Rope` API (confirmed via `rust-docs-mcp` structure inspection of `ropey 1.6.1`) natively provides `byte_to_char`, `byte_to_line`, `char_to_utf16_cu`, `utf16_cu_to_char`, and O(log n) `insert`/`remove` over a balanced B-tree-of-chunks structure — precisely the operations the *live open-buffer* case needs (cheap edits without re-copying the whole document string, native UTF-16 conversion without hand-rolling one). Markdown Oxide already uses `ropey` in production for exactly one purpose — converting regex-match byte offsets into LSP `Range`s (`research/markdown-oxide.md:41`) — not for incremental parsing; that's the right-sized adoption, not a wholesale text-model rewrite. **Recommendation: use `ropey::Rope` as the live-document text representation for open buffers (ticket 14's territory) and its conversion methods for byte→UTF-16 at the response boundary; keep parsing itself as "extract the current full text, hand it to `pulldown-cmark`, full re-parse" — do not chase rope-integrated incremental re-lexing, no peer does it and the payoff is unproven at Traces' target scale.**

**Persistence**: do **not** persist spans in the redb `FileIndex`. Three independent reasons converge: (1) spans are cheap to recompute — re-parsing a file the LSP just read (to serve a request against it) also re-derives every span in the same pass, at effectively the cost already being paid for the `Note` itself; (2) persisting spans means every edit invalidates persisted span data the instant the file's bytes shift by even one character, so the persisted copy is stale far more often than it's useful, for a value that's cheap to regenerate — this is the textbook shape of a cache with a worse hit-rate-to-maintenance-cost ratio than not caching; (3) it's a real, avoidable index-format version bump and migration/rebuild-on-load cost (the ticket names this correctly) for a feature (closed-file requests without reparsing raw Markdown) that doesn't obviously need it — `QueryService::execute`/`SchemaService` operations that only need `FileBase`/frontmatter-level facts already work off the persisted `Note` without spans; only *live-editing-session* requests (hover, completion, rename) need spans, and those are, by definition, against a file whose current text the LSP already has to touch.

## External precedent comparison

- **Markdown Oxide**: regex-only, no formal AST; `ropey::Rope` used solely to convert byte offsets from regex matches into LSP `Range`s. In-memory only, no persistence — the opposite extreme from Traces. **Adopt**: the narrow, correct-sized use of `ropey` for offset conversion. **Reject**: the no-AST/no-persistence model entirely — irrelevant, Traces already has a real parser and a persistent index, going backward to regex-only would be a regression, not an improvement.
- **Marksman**: Markdig's `SourceSpan`, translated to LSP `Range` via a line map; **fully re-parses on every edit**, confirmed with no incremental patching despite an elaborate suffix-tree workspace index. This is the closest architectural peer to what Traces should become: real AST, real spans, full re-parse per edit, incrementality only at the workspace-index (add/remove one document) level — exactly Traces' `IndexDelta` shape already. **Adopt**: this is confirmation, not a new idea — Traces' existing whole-file-reparse model is the same shape a mature, actively-used PKM LSP chose deliberately, not a shortcut to graduate away from.
- **Microsoft `vscode-markdown-languageservice`**: standard `vscode-languageserver-textdocument`, UTF-16 only, no `positionEncoding` negotiation. **Adopt**: nothing architecturally (it's a TypeScript library, different language entirely) but it sets the "must correctly serve a non-negotiating client" bar cited above, and its protocol-agnostic-library/thin-LSP-adapter split (already noted in ticket 05's research) is a pattern Traces' own module boundaries (Note/Index/Query as protocol-agnostic, LSP crate as the thin adapter, per ticket 09/10's resolutions) already match.
- **rust-analyzer**: VFS treats files as opaque IDs with **no `std::path::Path` concept internally**, editor buffer is the sole source of truth for open-file content, disk IO only for files the editor hasn't opened (`research/rust-analyzer-precedent.md:24-25`) — directly reusable for ticket 14's live-buffer-vs-filesystem question, independent of the spans decision. Its "parsing must never fail" invariant (partial/recoverable trees, not `Result<T, Error>`) is the thing that actually determines whether an LSP feels responsive while the user is mid-edit — `pulldown-cmark`'s event-stream model already has this property structurally (a malformed Markdown construct just becomes plain text in the event stream, it doesn't abort parsing), so Traces gets this invariant for free from its existing parser choice, another point in favor of not switching parsers.

## Crate/technology evaluation

**`pulldown-cmark`** (currently pinned, confirmed via `Cargo.toml`/direct source use): *Source/API*: `into_offset_iter()` already used (`parser.rs:104`), gives `Range<usize>` (UTF-8 byte offsets) per event, block and inline alike — confirmed by direct inspection, not assumed from crate docs. *Ecosystem*: "the industry standard in Rust" for CommonMark rendering (its own docs, corroborated independently). **Keep.**

**`yaml_serde`** (pinned `0.10.4` per `Cargo.lock`, the actively-maintained community successor after the original `serde_yaml` was archived by its maintainer in 2024 — this lineage fact matches the pattern already established for `tower-lsp`→`tower-lsp-server` and `tower-lsp`→ the Markdown Oxide fork in prior tickets' research, worth naming explicitly since it's the same "original archived, community fork is now the actual default" shape recurring a third time in this map). *Source/API*: confirmed via `rust-docs-mcp` — **no span/marker/location type reachable from a successfully-parsed `Value`**; `Location` exists only in `yaml_serde::error`, for parse-failure reporting. *Ecosystem*: this is the standard choice for YAML-via-serde in the current Rust ecosystem (no evidence of a better-adopted alternative for this exact use case), but it is **not** the right tool for span-aware frontmatter parsing regardless of adoption — the API simply doesn't expose what's needed. **Keep for what it's used for (typed frontmatter deserialization); do not lean on it for spans; add a separate raw-text re-scan for frontmatter-field positions.** (A spanned-YAML alternative such as `saphyr` exists in the ecosystem but was not deep-dived here — not recommended without first confirming a hand-rolled re-scan of Traces' typically-flat frontmatter is actually insufficient; introducing a second YAML dependency purely for spans on flat key-value data is very likely unjustified complexity per the map's own "introduce abstractions only for real boundaries" standing constraint.)

**`ropey`** (not currently a dependency): *Source/API*: confirmed via `rust-docs-mcp` structure inspection — B-tree-of-chunks `Rope`, O(log n) edit/query operations, native `byte_to_line`/`byte_to_char`/`char_to_utf16_cu`/`utf16_cu_to_char`. *Ecosystem*: the de facto standard Rust rope crate, already in production use by a directly-comparable peer (Markdown Oxide) for exactly the narrow role recommended here. **Adopt, scoped to live-buffer text representation and UTF-16 conversion — not as a parser-integration/incremental-reparse mechanism.**

**`tree-sitter` / `tree-sitter-markdown`** (not currently a dependency): *Source/API*: native `InputEdit`-based incremental re-parsing — real capability, not marketing. *Ecosystem*: web-verified (2026) as mature for editor-highlighting/folding use cases specifically, explicitly not recommended where parsing correctness is paramount; zero adoption among every Markdown/PKM LSP peer studied in this map. **Reject** for Traces' core parser. (Could theoretically be evaluated later, narrowly, if a specific feature — e.g. embedded-code-block language-aware highlighting — turns out to need it; not justified for the span/position model this ticket is about.)

**`miette`** (already a dependency, already used for query diagnostics): *Source/API*: `SourceSpan` = `(offset: usize, length: usize)`, `#[source_code]`/`#[label]` derive macros already proven working in `src/query/error.rs`. **Reuse directly** for any future Note-parse diagnostic — this is not a new integration, it's extending an existing one to a second producer.

## Codebase-change recommendations

**Required for correctness** (LSP hover/definition/references/rename cannot be built without these, full stop):
- Add `Range<ByteOffset>` (or equivalent) fields to `Link`, `Tag`, and inline-field entries — capture `range.end`, not just `range.start`, from `pulldown-cmark`'s `into_offset_iter()` and from `logos` token spans in `InlineTokenLexer`.
- Widen `ByteOffset` (`src/position.rs:97`) from `pub(crate)` to `pub`, and `ByteTracker` (`src/note/parser/line.rs:7`) from `pub(super)` to at least crate-public, so LSP-facing code outside `note::parser` can convert offsets.
- Design and add a `Heading` AST node — currently structurally absent, not just span-less; needed for document symbols, folding, heading-anchor links, and heading-reference resolution regardless of the spans question.

**Required for performance at large-vault scale**:
- None of the above materially affects large-vault performance — spans are small, per-note, and (per the Persistence recommendation) never held for the whole vault simultaneously. The actual large-vault performance risk this research reconfirms is the one ticket 38 already flagged: `QueryService::matched_file_rows`'s linear scan (`src/query/service.rs:207-211`) — unrelated to spans, ticket 33's job.

**Strongly recommended simplification**:
- Extend `ByteTracker` with a UTF-16 code-unit conversion method (either hand-rolled over its existing line-start table, or by adopting `ropey`'s equivalent methods for the live-buffer case specifically) rather than building a second, parallel line-index abstraction — one canonical line-index type, not two.
- Add a small dedicated frontmatter raw-text scanner (walks `RawFrontmatter`'s preserved string, maps top-level — and shallow-nested, if needed — YAML keys to byte ranges) rather than attempting to retrofit spans onto `yaml_serde::Value`.

**Optional/future optimization**:
- `ropey::Rope` adoption for open-buffer text (ticket 14's territory) — clearly beneficial, but its exact integration point is ticket 14's decision, not this ticket's.
- A spanned-YAML crate (e.g. `saphyr`) if the hand-rolled frontmatter scanner proves insufficient for genuinely nested frontmatter structures in practice — evaluate only if the simpler approach demonstrably fails.

**Not worth it**:
- Switching the core Markdown parser away from `pulldown-cmark` (tree-sitter-markdown or otherwise) — zero precedent, real correctness risk, no demonstrated need.
- Persisting spans in the redb `FileIndex` — real migration cost, poor cache-hit shape (invalidates on every edit), no clear beneficiary given spans are cheap to recompute from a file the LSP is already re-reading.
- A parallel LSP-only span index built alongside (not inside) the `Note` AST — would duplicate the position-computation work the parser is already doing in the same pass, and would violate the map's own "reuse existing services... rather than building parallel LSP-only models" standing constraint for no offsetting benefit over just extending `Note` directly.

## Final recommendation

Extend, don't replace: add spans to the existing `Note` AST types (`Link`, `Tag`, inline fields, plus a new `Heading` node), computed transiently from `pulldown-cmark`'s already-available `Range<usize>` per event and `logos`' already-available per-token spans, converted to `SourceLine`/UTF-16 via a widened `ByteTracker` at the LSP-response boundary only. Do not persist spans in redb. Do not switch the core parser. Adopt `ropey`, narrowly, for the live-open-buffer text representation (ticket 14's integration point). Handle frontmatter separately via a small raw-text re-scanner, because `yaml_serde` has no span capability to lean on. This is the smallest change that is also, independently, the *correct* first-principles answer — the two did not conflict in this investigation, which is itself worth stating plainly rather than manufacturing a bigger-change recommendation where the evidence doesn't support one.

## Open questions still requiring grilling with the user

1. **Byte-offset width**: `u32` (4 GiB/file cap, saves 8 bytes per span vs. `usize`) or keep `usize` matching `ByteOffset`'s current representation? Pure implementation-spec detail, but worth deciding once, consistently, rather than per-caller.
2. **Heading node design**: does a `Heading` need to track its nesting level/parent relationship structurally (a real tree), or is a flat list with a level field sufficient for symbols/folding? This is a genuine design fork this research surfaces but doesn't resolve — depends on how ticket 27 wants to consume it.
3. **Frontmatter re-scanner depth**: does it need to handle arbitrarily nested YAML (lists of objects, etc.) or is flat/one-level-nested sufficient for Traces' actual schema/File-Class field shapes? Affects whether the hand-rolled scanner is trivial or needs real YAML-structure awareness. Needs a look at real Traces vault frontmatter shapes, not just the type definitions, to answer confidently.
4. **UTF-16 conversion ownership**: should the conversion live in the widened `ByteTracker` (extending the existing type) or as a `ropey`-backed alternative used only for open buffers, with `ByteTracker` staying byte/line-only for closed-file/persisted-index use? Two call sites with different needs (live buffer vs. closed-file read) might genuinely want two different (but consistent) implementations — worth deciding explicitly rather than defaulting to one without considering the split.
5. **Confirm with the user directly**: does the actual Traces vault (the one that broke Obsidian and Markdown Oxide) have any frontmatter/inline-field shapes complex enough to stress-test recommendation 3 above, or heading-nesting depth that stress-tests recommendation 2? This research reasoned from the type definitions and general PKM-vault assumptions, not from a real large-vault sample — worth checking before ticket 11's grilling session locks in the Heading/frontmatter-scanner design.
