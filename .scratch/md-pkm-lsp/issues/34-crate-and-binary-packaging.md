# Crate/binary packaging & integration into the Traces build

Type: grilling
Blocked by: 09, 10

## Question

Grounding: Traces is currently a **single package**, not a Cargo workspace (`Cargo.toml` has one `[package]`, no `[workspace]` table), producing one binary (`traces-pkm`, `src/main.rs`) that wraps the library crate's `pub mod cli` entrypoint (`cli::run()`). Treat that as the starting state only, **not** a constraint to preserve — adding a comprehensive LSP is a large enough addition that converting to a Cargo workspace is a live, expected-not-exotic option, not a "larger structural change" that needs to clear a higher bar than staying single-crate. Once the framework/runtime (09) and analysis-host (10) decisions are settled, decide:

- Where LSP code lives: a new `src/lsp/` module inside the existing single crate vs converting to a Cargo workspace with a separate `traces-lsp` (or similarly named) crate depending on the existing crate's `test-utils`-gated public API. Weigh both directions, not just one: workspace separation cleanly keeps "LSP protocol DTOs and client-specific concerns... at the protocol boundary" (a standing constraint), isolates the CLI binary's dependency footprint/build time/binary size from whatever ticket 09 selects, and forces the core crate's LSP-facing API to be deliberately designed rather than incidentally exposed — but it also means two crates to version in lockstep, a `pub` surface on the core crate that has to be gotten right upfront (or churned across two `Cargo.toml`s as the LSP's needs evolve), and duplicated CI/lint/release configuration (`clippy.toml`, `deny.toml`, `rustfmt.toml` etc. would need workspace-level or per-member handling — check which). A single-crate module has the inverse trade: no crate-boundary API design tax today, one `Cargo.toml`/one release cadence, but real risk of the LSP's concerns leaking into what's currently a clean `pub`/`pub(crate)` split (`src/lib.rs`'s existing `test-utils`-gated re-export pattern) as the LSP surface grows, and it permanently couples the CLI binary's dependency graph to the LSP's unless the feature-flag boundary below is maintained with discipline over time. Neither is free; pick based on how the LSP's actual shape (once 09/10 are known) stresses each trade-off, not on which one is less work to start.
- Binary/invocation shape: a new `[[bin]]` target (e.g. `traces-lsp`) that clients launch directly, vs a hidden `traces lsp` CLI subcommand (reusing the existing `clap` `Commands` enum in `src/cli/mod.rs`) that starts the server over stdio — check what convention rumdl (`rumdl server`) and Marksman/Markdown Oxide use as precedent (tickets 01-03) for what editor-integration configs will expect. A separate `[[bin]]` is the natural fit if a workspace split is chosen; a subcommand is the natural fit if the single-crate module is chosen — let that follow from the packaging decision, not force it.
- Feature-flag boundary: if the single-crate module is chosen, does the existing `test-utils` feature-flag pattern (already used to expose otherwise-`pub(crate)` items to `tests`/`benches`) extend to gate LSP-only code so a plain `cargo build` for CLI-only use doesn't pull in LSP dependencies by default. (Moot if a workspace split is chosen — separate crates already have separate dependency graphs.)
- Release/packaging implications (`profile.release` already sets `panic = "abort"`, `lto = true`, `codegen-units = 1`, `strip = true` — confirm these remain compatible with whatever runtime ticket 09 selects, e.g. `panic = "abort"` interacting with any async runtime's panic-handling expectations, and confirm workspace-wide vs per-crate profile inheritance if a workspace split is chosen).
