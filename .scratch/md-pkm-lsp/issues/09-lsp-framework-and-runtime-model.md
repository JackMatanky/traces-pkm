# LSP framework/transport crate & runtime model

Type: grilling
Blocked by: 07
Status: claimed

## Question

Traces' codebase is synchronous *today* (no tokio/async-std anywhere; confirmed by repo-wide grep) — treat that as the starting state only, **not** a constraint. Adopting an async runtime (`tokio`, or another async primitive/channel crate) for the LSP addition is a live, unbiased option, not a deviation that needs special justification; so is converting to a Cargo workspace (see ticket 34, which this ticket's choice directly shapes) if that's the cleaner place to draw the boundary. Decide on the merits of what the LSP process actually needs, informed by [Rust LSP framework crate research](../research/rust-lsp-framework-crates.md) — that research answers "what exists and what it demands" per crate, it does not itself pick a winner:

- Which crate(s) provide the JSON-RPC/LSP transport and protocol DTOs (`lsp-server`+`lsp-types`, `tower-lsp-server`, `async-lsp`, or other) — weigh each candidate on **two separate axes**, per [the corrected research](../research/rust-lsp-framework-crates.md): (1) raw runtime-model fit with whatever ticket 09 decides about the core (below), and (2) ecosystem maturity, documentation, and implementation velocity — `tower-lsp-server` (the actively-maintained `tower-lsp-community` fork, not the abandoned original `tower-lsp`) is the current de facto standard, most-tutorialed, lowest-onboarding-cost choice in the wider Rust LSP ecosystem; `lsp-server` is the deliberately low-level option rust-analyzer chose for reasons specific to also building its own incremental query engine, not evidence it's the generally-recommended default. Don't let axis (1) alone decide this — a real ecosystem/velocity advantage for `tower-lsp-server` can legitimately outweigh a sync-core-fit advantage for `lsp-server`, especially if it also tips the async-runtime question below.
- Whether the LSP process takes on an async runtime, and if so how far it reaches: transport-loop-only (sync worker threads for request handling) vs whole-process-async (every Index/Query/Schema/Template call wrapped for the async context). Weigh both real costs, not just one side: the research finding that `tower-lsp`-family cancellation (drops a `Future`) doesn't interrupt `spawn_blocking`'d synchronous work is a real cost of a hybrid sync-core/async-transport shape; moving the core itself onto async primitives (e.g. running Index/Query calls as blocking tasks under `tokio`, or adopting async-friendly concurrency primitives more broadly) has its own real costs — `async fn` in traits/public APIs propagates outward through every caller, `tokio` (or another runtime) becomes a mandatory dependency of whatever crate the async code lives in (a plain `cargo build` for CLI-only use pulls it in unless ticket 34's packaging keeps it isolated), and it's a larger rewrite of already-working, already-tested synchronous code for a benefit (true async cancellation) that a cooperative-checkpoint approach in the hot loops (per ticket 12) may deliver for less. Neither option is free; decide based on what ticket 12's cancellation-checkpoint design actually needs, not on which one sounds more modern.
- How this interacts with Template rendering's synchronous, blocking `DialogProvider` I/O (`src/template/engine/ui.rs`) — an LSP request handler must never block on human input the way CLI template instantiation does; decide whether template-related LSP features simply never invoke `ui.*` helpers (static analysis only, see ticket 22) or whether a non-interactive `DialogProvider` implementation is needed for some code path. This holds regardless of the sync/async choice.
- Base protocol handling (Content-Length framing) — confirm the chosen crate covers it or whether it needs implementing.

This is the foundational decision most other architecture tickets (10, 12, 21, 23, 26, 34) depend on.
