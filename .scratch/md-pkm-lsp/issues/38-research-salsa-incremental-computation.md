# Research: salsa/incremental-computation frameworks — timing and cost of adopting now vs. later, and root cause of large-vault performance problems

Type: research
Blocked by:
Status: resolved

## Question

Ticket [Analysis host architecture & integration with IndexerService/QueryService/SchemaService](10-analysis-host-and-index-integration.md)'s Q4 asks whether Traces adopts a salsa-style incremental query engine now or defers that decision to ticket 33 (performance targets & strategy) once it has concrete numbers. The user is leaning toward deciding now, because the primary motivation for this entire project is that both Obsidian itself and the Markdown Oxide LSP failed to handle their large vault — crashing or becoming very slow.

Investigate, with citations:

- **How salsa actually works**: memoized, dependency-tracked queries, revision-based invalidation, `#[salsa::tracked]`/`Database` trait shape. Use `rust-docs-mcp` to cache and inspect the crate directly (not memory) — confirm current version/API shape.
- **Architectural cost of timing**: does adopting Q1's answer now (`Arc<FileIndex>` behind a swap-on-refresh point, whole-file invalidation) foreclose or materially complicate layering salsa-style incremental query memoization in *later*, once ticket 33 sets targets — or is it a compatible, extensible foundation (e.g. because salsa queries can wrap/read from an `Arc<FileIndex>`-shaped input without the host's sharing strategy needing to change)? Rust-analyzer is the primary evidence here — read [its precedent research](../research/rust-analyzer-precedent.md) and, if it doesn't already answer this, go back to source for how salsa integrates with rust-analyzer's `AnalysisHost`/`Analysis` split specifically (is salsa the thing *inside* `Analysis`, or a separate layer?).
- **Root cause of the user's actual pain**: is Obsidian's/Markdown Oxide's large-vault slowness or crashing actually caused by a *lack of incremental computation* (re-running everything on every keystroke), or by something else entirely (unbounded memory growth, O(n) or worse linear/quadratic scans, lack of pagination, eager full-vault parsing on startup with no lazy loading, Electron/JS overhead in Obsidian's own case)? Check the existing research files first — [markdown-oxide.md](../research/markdown-oxide.md) (regex-only/no-AST/in-memory-only/`MAX_INDEXED_LINES = 10_000` cap already documented; rayon-parallelized), [marksman.md](../research/marksman.md) (full re-parse per edit, actor-model), [dataview-templater-metadatamenu-parity.md](../research/dataview-templater-metadatamenu-parity.md) (Obsidian plugin-level findings) — then supplement with targeted web search for documented Obsidian/Markdown-Oxide large-vault performance reports/issues if the local corpus is silent. This determines whether salsa-style incrementality is actually the fix for the user's stated problem, or whether a different, cheaper intervention (e.g. avoiding full-file re-parse, bounding memory, avoiding `QueryService`'s linear scan at scale) would address the *actual* root cause without the cost of adopting salsa now.
- A concrete recommendation for ticket 10's Q4: adopt salsa now, explicitly defer to ticket 33, or a third option this research surfaces.

## Answer

**Defer salsa adoption to ticket 33 — but the reasoning matters more than the vote.** Architecturally, deferring costs nothing: rust-analyzer's own source (`crates/ide/src/host.rs`) confirms `AnalysisHost`/`Analysis` is the exact shell that houses its `salsa::Database` (`RootDatabase`) — building the `Arc<FileIndex>` Host/Snapshot boundary now is a compatible, extensible foundation, not a deviation that later needs undoing; `Arc<FileIndex>` can be swapped for a `salsa::Database` later without rewriting LSP request routing.

**The more important finding is root cause**: salsa-style incremental *query* memoization is very likely not the fix for the large-vault pain that motivated this whole project. Obsidian's core handles 10k+ notes fine — its slowness/crashes are attributed (web-verified) to **plugin-level unindexed O(N) linear scans across the whole vault on every render/edit**, Dataview foremost among them, plus sync-service churn. Markdown Oxide's failure mode is **unbounded memory growth and O(N) whole-vault CPU load** from its eager, in-memory-only, no-persistence, regex-based indexing — not a lack of incremental re-computation. Both are addressed by architecture Traces already has or is building (persistent `redb` index, targeted lookups), not by salsa.

**This is not just background — it is a direct warning about Traces' own current code**: `QueryService::execute`'s source resolution is *already* a linear scan of every `FileIndex` entry (`src/query/service.rs:132-139` — the same "reuse vs. performance" tension the map already flags). That is structurally the identical failure shape just found in Dataview. Adopting salsa would not fix this — salsa memoizes derived-query *results* across edits, it doesn't parallelize or index a linear scan's *first* execution. If `QueryService`'s scan is the thing that chokes at the user's vault scale, the fix is indexing/parallelizing that scan (or building a real lookup structure), not salsa — and this needs to be evidenced with real numbers, which is exactly ticket 33's job.
