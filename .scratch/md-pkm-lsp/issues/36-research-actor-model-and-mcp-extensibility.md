# Research: actor-model/event-driven architecture for the analysis host, and future MCP-server extensibility

Type: research
Blocked by:
Status: resolved

## Question

Ticket [Analysis host architecture & integration with IndexerService/QueryService/SchemaService](10-analysis-host-and-index-integration.md)'s Q1 asks how the analysis host shares `FileIndex` state across concurrent LSP request handlers. The user picked (a) `Arc<FileIndex>` behind a swap-on-refresh point, but asked for thorough research on the rejected alternative — (c) an actor/message-passing model, where a dedicated task owns `FileIndex` state and handlers send it query/refresh requests over a channel — because event-driven architecture has general benefits, and might matter for a **future MCP (Model Context Protocol) server** built atop the same Index/Query/Schema services (a second protocol frontend alongside the LSP, not yet a ticket on this map — out of this effort's destination, but the *architectural door* to it is the live question here).

Investigate:
- Real Rust actor-model crates/patterns for this shape (hand-rolled `tokio::sync::mpsc`-based actors, `ractor`, `actix`, `xtra`, `kameo`, or similar) — maturity, adoption, and what they actually buy over a plain channel + task loop.
- What concrete architectural benefits an actor/message-passing core offers over a shared-immutable-snapshot (`Arc`-swap) model — for concurrent access, extensibility, decoupling multiple consumers.
- **The MCP-extensibility question directly**: does an actor-model core make it materially easier to later expose the same coordinator to a second protocol frontend (MCP server) without duplicating logic or rearchitecting, compared to the `Arc`-swap facade approach (ticket 10's Q3) — i.e. is "one coordinator, N protocol adapters calling its public API" already sufficient regardless of whether the coordinator's internals use a swap cell or a mailbox, or does the mailbox shape genuinely unlock something (e.g. built-in request queuing/backpressure/streaming that an ad-hoc `Arc`-swap facade would have to hand-build)?
- Real precedent already in this map's research: Marksman uses an actor model (F#'s `MailboxProcessor`) for its concurrency — read [Marksman's research findings](../research/marksman.md) and (if needed) the source directly via the local digest (`docs/digests/lsp_artempyanykh-marksman-*digest.txt`) for *why* it chose that shape and whether that reasoning transfers to Traces' situation (in-memory suffix-tree workspace index vs. Traces' redb-backed persistent index). Also check whether rust-analyzer, Biome, `ty`, or `ruff server` (already researched — see [rust-analyzer precedent](../research/rust-analyzer-precedent.md) and [performant Rust LSP runtime models](../research/performant-rust-lsp-runtime-models.md)) use an actor-model core internally for this specific purpose (index coordination), and why or why not.

## Answer

**Reject the actor model, confirm `Arc<FileIndex>` swap-on-refresh.** An actor/message-passing core provides zero unique benefit for MCP extensibility — "one coordinator, N protocol adapters" is already trivially satisfied by an `Arc`-swap facade (LSP loop and a future MCP loop each hold a clone of the same `Arc<Coordinator>` and call ordinary Rust methods; neither needs to know the other exists). Worse, an actor model actively hurts here: an LSP/MCP workload is overwhelmingly read-heavy, and routing every read through a single actor's channel queue serializes what should be concurrent lock-free reads — to fix that the actor would just have to hand back an `Arc<Snapshot>` anyway, making it a slower, more complex `RwLock`. Zero precedent among performant Rust LSPs (rust-analyzer, Biome, `ty`, `ruff server`) for an actor-model index core; Marksman's actor model (F#'s `MailboxProcessor`) is idiomatic to F#, not evidence for Rust, and its index stays fully in-memory with full re-parse per edit — doesn't map to Traces' persistent-index situation. [Full findings](../research/actor-model-and-mcp-extensibility.md).
