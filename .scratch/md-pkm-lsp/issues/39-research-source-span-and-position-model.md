## Question

If changing any of them (parser strategy, AST shape, persisted schema, module boundaries) is what a fast, low-memory, correct design requires, say so explicitly — do not default to the smallest diff.

## Answer

**`pulldown-cmark` is already opted into byte-range-per-event** (`into_offset_iter()`, `src/note/parser.rs:104`) but only `range.start` survives past `handle_event`, used solely for list-item line tracking — the raw span data for links/tags/headings/inline fields exists at parse time today and is discarded, not absent by parser limitation. This makes "extend the existing AST" a materially easier and better-evidenced answer than a parser swap.

Three separable questions, resolved independently: (1) **Do spans go on the `Note` AST directly?** Yes — extend `Link`/`Tag`/inline-field types, add a first-class `Heading` node (currently structurally absent, a real gap this research surfaces beyond what ticket 11's wording named). (2) **Does the parser change?** No — zero precedent among every studied peer (Markdown Oxide regex-only, Marksman Markdig-full-reparse, Microsoft's own generic-Markdown service) for tree-sitter-markdown, and it's web-confirmed (2026) as explicitly not recommended where parsing correctness matters — a real risk given Traces' custom inline-field/wikilink syntax on top of CommonMark. (3) **Rope/incremental adoption?** `ropey` adopted narrowly for live-open-buffer text + UTF-16 conversion (Markdown Oxide's exact production use of it); full re-parse per edit stays correct — every peer studied does full re-parse, none does parser-level incrementality.

**Frontmatter is the hard case, confirmed empirically, not assumed**: `yaml_serde` (the pinned `0.10.4`) has zero span/marker capability reachable from a successfully-parsed `Value` — its only `Location` type is scoped to parse-failure errors (verified directly via `rust-docs-mcp` against the exact crate version in `Cargo.lock`). Frontmatter spans need a dedicated raw-text re-scan of the already-preserved `RawFrontmatter` string, not a YAML-crate feature.

**Persistence**: spans should stay transient (computed at LSP-request time from source text already being re-read), never persisted in redb — real migration cost, poor cache-hit shape (invalidated by any edit), no clear beneficiary since spans are cheap to recompute in the same pass that already re-parses the file.

**LSP protocol**: verified against the primary spec (not the local `docs/refs/lsp_spec.md`, confirmed to be an unresolved include-skeleton for the relevant fragment) — UTF-16 is the default encoding, LSP 3.17's `positionEncoding` negotiation is opt-in per-client, and the canonical generic-Markdown baseline (Microsoft's own service, ticket 05) doesn't negotiate at all — any design must correctly serve non-negotiating UTF-16-only clients, not treat that as a legacy edge case.
