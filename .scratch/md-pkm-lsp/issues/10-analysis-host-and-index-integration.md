# Analysis host architecture & integration with IndexerService/QueryService/SchemaService

Type: grilling
Blocked by: 09, 36, 37, 38
Status: resolved

## Question

Decide how the LSP process wraps and reuses the existing synchronous services rather than building parallel models, per the standing constraint "Reuse existing Traces semantics and services rather than building parallel LSP-only models."

Grounding facts already gathered:
- `FileIndex` (`src/index/entry.rs:23`) is an immutable, single-owned (not `Arc`-shared today), `Clone`-able snapshot: `entries: Box<[FileEntry]>` + `delta: IndexDelta`. `IndexerService` (`src/index/service.rs`) exposes `build`/`refresh`/`persist`/`load`, all synchronous, all manually triggered (no filesystem watcher exists anywhere in the codebase today).
- `QueryService::execute(&self, index: &Arc<FileIndex>, builder: QueryBuilder) -> QuerySet` (`src/query/service.rs:84`) already expects an `Arc<FileIndex>` at the call boundary, even though `IndexerService` itself doesn't produce one internally — note this seam.
- `SchemaService` (`src/schema/service.rs`) is a load-once, in-memory-cached registry (`IndexMap<SchemaName, Arc<Schema>>`), resolved once at startup, not re-resolved per query.
- Indexing/refresh today is single-threaded with no `rayon`/parallelism.

Decide:
- Whether the LSP host wraps a single `Arc<FileIndex>` behind a swap-on-refresh cell (à la prior "immutable/queryable snapshots" hypothesis) shared read-only across concurrent request handlers, versus some other sharing strategy.
- What triggers an index refresh in LSP mode: `didSave`, `didChangeWatchedFiles` (LSP file-watching capability — consult `docs/refs/lsp_spec.md`), a debounced timer, or something else — given there's no existing filesystem-watcher crate/dependency in Traces today, decide whether one gets added (and which — check via rust-docs-mcp if not already covered by the chosen LSP framework) or whether LSP-side didChange/didOpen/didSave notifications are sufficient without OS-level file watching.
- Whether `QueryService`/`SchemaService` get wrapped by a thin analysis-host facade or invoked directly per-request.
- How this interacts with the rust-analyzer host/snapshot precedent (ticket 06) — confirm, refine, or reject that hypothesis for Traces, including whether Traces adopts an incremental query engine (salsa-style or otherwise) alongside the host/snapshot split, or whether a coarser whole-file-invalidation model is sufficient; don't presume the answer either way before weighing it against ticket 33's performance targets.

Blocks: 12(concurrency), 13(persistence/caching), 14(live-buffer overlay), 30(multi-root), 34(packaging).

## Answer

**Sharing strategy**: a single `Arc<FileIndex>` behind a swap-on-refresh cell (e.g. `RwLock<Arc<FileIndex>>` or equivalent — the exact primitive is an implementation-spec detail, not decided here), shared read-only across concurrent request handlers. Matches the already-grounded seam (`QueryService::execute` already expects `Arc<FileIndex>` at its call boundary) and rust-analyzer's Host/Snapshot precedent (ticket 06). An actor/message-passing alternative was researched thoroughly (ticket 36, prompted by wanting to keep a future MCP server easy to add) and rejected: it provides zero unique benefit for "one coordinator, N protocol frontends" — an `Arc`-swap facade already gives that for free via ordinary method calls — while actively serializing what should be concurrent lock-free reads. Zero precedent among performant Rust LSPs (rust-analyzer, Biome, `ty`, `ruff server`) for an actor-model index core.

**Refresh trigger**: `workspace/didChangeWatchedFiles` (server registers glob patterns via dynamic registration; the *client* does OS-level watching and notifies the server — confirmed against the primary LSP spec, since the local `docs/refs/lsp_spec.md` copy is an unresolved include-skeleton for this fragment) is the primary mechanism, requiring no new Rust dependency. `didOpen`/`didChange`/`didSave` continue to cover the open-buffer editing lifecycle incidentally. A Traces-owned filesystem watcher (`notify`+`notify-debouncer-full`, researched in ticket 37) was considered for broader codebase benefit and explicitly **not adopted here** — zero precedent among studied tools for bundling one alongside LSP-provided watching, and no concrete non-LSP consumer exists yet to justify it. Real future gaps identified: a `traces watch` CLI mode (no daemon/watch mode exists today) and the future MCP server if its clients turn out not to offer file-watching capability — neither in scope for this ticket; revisit as a distinct ticket if/when either is actually being built.

**Facade**: a thin analysis-host facade wraps `QueryService`/`SchemaService`, owning the `Arc<FileIndex>` swap point and the cached `SchemaService`, handed to every request handler — rather than handlers instantiating/calling those services directly. Gives tickets 13 (persistence/caching) and 14 (live-buffer overlay) one integration point instead of scattered access, and matches rust-analyzer's `AnalysisHost` shape. Stays a thin composition point (services + swap cell), not a place to grow independent logic.

**Incremental query engine (salsa) timing**: confirmed as (a) — defer to ticket 33 (performance targets & strategy), do not adopt salsa now. Architecturally this costs nothing: rust-analyzer's own source confirms `AnalysisHost`/`Analysis` (the shape just adopted above) is the exact shell that houses a `salsa::Database` — nothing here forecloses adding salsa later without rearchitecting the LSP request-routing boundary. More importantly (ticket 38's research, prompted by the user's stated motivation — Obsidian and Markdown Oxide both failing on their large vault): **salsa is very likely not the actual fix for that pain.** Obsidian's core handles 10k+ notes fine; its slowness/crashes trace to Dataview running unindexed O(N) scans across the whole vault on every render. Markdown Oxide's failure is unbounded in-memory growth from zero persistence, not missing incrementality. Neither is "recomputation isn't memoized" — both are "no index, no bound." **Load-bearing flag for ticket 33**: `QueryService::execute`'s source resolution is *already* a linear scan over every `FileIndex` entry (`src/query/service.rs:132-139`) — structurally the same failure shape just found in Dataview. Salsa would not fix that scan (it memoizes results across edits, it doesn't index or parallelize a scan's first execution); if that scan is what chokes at target vault scale, the fix is indexing/parallelizing it, evidenced with real numbers — ticket 33's job.
