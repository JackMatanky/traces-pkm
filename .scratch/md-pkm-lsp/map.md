# Traces Markdown/PKM Language Server — design map

## Destination

Reach a fully settled design for the Traces Markdown/PKM language server — including the architectural changes needed to integrate it coherently with the existing Traces codebase — such that the completed map can be converted into an implementation specification without unresolved material product, semantic, architectural, interoperability, or performance decisions.

Product shape: **Traces LSP** owns Markdown semantic/editor intelligence and PKM intelligence; **rumdl** owns Markdown linting, formatting, and lint-oriented fixes. A user running Traces together with rumdl needs no other Markdown LSP (Markdown Oxide, Marksman, Microsoft's markdown-language-server) for comprehensive Markdown semantic/editor functionality. Traces must cover at least the valuable generic Markdown language-service capabilities and the full useful PKM capability set of Markdown Oxide, while extending beyond both through Traces' existing/planned Templater-, Dataview-, and Metadata-Menu-inspired functionality.

This is a **planning-only** effort: no production code is written or modified while working this map. Throwaway prototypes are permitted only when genuinely necessary to resolve a design question.

## Notes

**Skills**: every grilling-type ticket invokes `/grilling` and `/domain-modeling`. Every research-type ticket is resolved by a `/research` subagent. Prototype-type tickets (none created yet; may be added later if a "how should it look/behave" question surfaces) invoke `/prototype`.

**Local research corpus**: prefer `docs/refs/lsp_spec.md` (LSP 3.18 spec) and `docs/digests/*.txt` (Markdown Oxide, Marksman, rumdl, zk, plus bonus Obsidian-plugin digests for Dataview/Templater/Metadata-Menu/obsidian-tasks) over live fetches; read directory structure first, then targeted sections. Use `rust-docs-mcp` as the primary source for Rust crate/API questions. Fall back to primary upstream sources (repos, official docs) when the local corpus is stale, incomplete, or silent.

**Research-ticket output convention (tracker-specific deviation)**: this repo's local-markdown tracker (`docs/agents/issue-tracker.md`) has no existing git-branch convention for research artifacts. Findings for each research ticket are written to `.scratch/md-pkm-lsp/research/<slug>.md` (plain files in this effort's directory) instead of a throwaway `research/<name>` git branch, and linked from the ticket's `## Answer`.

**Standing constraints** (apply to every ticket):
- Filesystem Markdown is the authoritative persistent source of truth; unsaved editor buffers must be reflected in live language intelligence without requiring disk writes.
- Reuse existing Traces semantics/services (Index, Query, Schema, Template, Config) rather than building parallel LSP-only models.
- LSP protocol DTOs and client-specific concerns stay at the protocol boundary; they never define core semantics.
- Preserve existing architecture where it remains suitable — do not refactor merely to conform to an abstract language-server pattern.
- Performance is first-class: initial indexing, incremental editor changes, interactive requests, and large PKM workspaces all need explicit targets (ticket 33).
- Prefer explicit, idiomatic Rust; strong domain types; clear ownership; simple interfaces; introduce abstractions only for real boundaries/invariants/reuse.
- Design intentional, documented coexistence with rumdl (ticket 32) rather than relying on accidental multi-LSP behavior.
- **Do not presume the current single-crate, synchronous status quo is sticky.** Converting to a Cargo workspace and/or adopting an async runtime (`tokio` or another async primitive) for the LSP addition are live, unbiased options for tickets 09 and 34 — evaluate them on their merits for the LSP's actual needs, not against a bar of "changes more than staying as-is."
- Prefer evidence from the existing repository, the local reference corpus, `rust-docs-mcp`, and primary upstream sources over assumptions from memory. (Dropped from the first draft of this list; restored 2026-09-03 after a research subagent violated it — see the methodology caveat below.)

**Named tension — reuse vs. performance**: "Reuse existing Traces semantics/services" and "performance is first-class... sub-100ms interactive requests" are in real, not hypothetical, tension. `QueryService`'s source resolution is a linear scan of every `FileIndex` entry (`src/query/service.rs:132-139`), `IndexerService::refresh` is a single-threaded whole-tree diff, and `Note` parsing is single-pass, full-file, no incremental re-parse — none of that was built for per-keystroke latency. Tickets 10, 12, 13, and 33 each touch a piece of this; none of them is authorized to quietly resolve the tension by picking "reuse as-is" as the path of least resistance. If reuse and the performance targets (once ticket 33 sets numbers) turn out incompatible at target scale, that conflict needs to surface explicitly in whichever ticket hits it first, not get smoothed over.

**Methodology caveat — research-subagent reliability**: the eight research findings below are single-pass, single-subagent reports, not independently cross-checked by a second reader before this map absorbed them. Three claims were spot-checked directly against primary sources while auditing this map (Marksman's documented-but-not-implemented duplicate-heading diagnostic; rumdl's `enableSymbols` setting; `tower-lsp-server`'s `future::abortable`-based cancellation) and all three held up — but that is three claims out of dozens across eight reports, not a full audit. One research subagent (ticket 07) also violated the "use `rust-docs-mcp`, not raw fetches" instruction by shelling out to `cargo clone` when its first `cache_crate` calls hit a tool-schema error, leaving `tower-lsp-server/` and `lsp-server/` as untracked directories in the repo root (found and deleted 2026-09-03; the underlying findings were re-verified and are accurate, but the process violation went uncaught until asked about directly — treat "subagent reported completed" as unverified until spot-checked, per the hub tool's own warning, not as settled fact). Treat any single research claim that later turns out to be load-bearing for a specific wording/threshold decision as worth a direct primary-source check before relying on it, especially anything from Marksman/rumdl's F#/Rust source (dense, easy to misattribute line numbers in) rather than their prose docs.

**Second confirmed instance (2026-09-03)**: ticket 07's research was also found to be one-sided in a different way — it answered "what does each crate's code demand" (via `rust-docs-mcp` and source archaeology) but never checked real-world ecosystem adoption, documentation quality, or practitioner consensus, then let the one axis it did check stand in for the whole question. A web sweep afterward confirmed `tower-lsp-server` (not `lsp-server`) is the current de facto standard/most-recommended Rust LSP framework across 2025/2026 tutorials and community discussion. General lesson: a research subagent restricted to source-code/API tools alone cannot answer "what's generally recommended" — that needs an explicit instruction to check practitioner consensus (web search, tutorials, forums), and I should have scoped ticket 07 that way from the start rather than letting a purely code-level investigation implicitly answer a socio-technical question.

**Full-audit pass (2026-09-03), prompted by the tower-lsp-server correction**: reviewed all eight research files and all 34 tickets for the same class of problem (an unverified authority/adoption/maintenance claim, or a "which technology" question answered from source-code archaeology alone). **Generalized rule** for every future ticket resolution that involves picking a crate, library, or technology (tickets 10's filesystem-watcher choice, 11's `ropey`/tree-sitter mention, 33's `rayon` mention, and any other not-yet-specified pick): answer both "what does the source/API demand" (rust-docs-mcp, crate source) *and* "what does the ecosystem actually reach for and why" (web search for current tutorials, comparison posts, practitioner discussion) as two separate, explicitly-scoped questions — never let one stand in for the other. A minor, secondary caveat: the Obsidian-plugin digests (`docs/digests/obsidian_*`) underlying ticket 08's research are ~3 months older than the LSP-reference digests (~hours old) — the Obsidian plugin ecosystem moves fast; the broad architectural patterns found (EditorSuggest-based completion, no LSP precedent for any of the four) are unlikely to have changed, but a specific implementation detail from that research should be re-verified against the live plugin source before being treated as load-bearing.

**Grounded baseline facts already established** (from direct repo investigation, so later tickets should treat these as given rather than re-deriving them):
- Traces is a **single Cargo package** *today*, not a workspace; one binary (`traces-pkm`, `src/main.rs`) wrapping `pub mod cli`. Starting state only — see the standing constraint above; ticket 34 decides whether this changes.
- The **entire codebase is synchronous** *today* — no tokio/async-std dependency, no `async fn` anywhere in `src/`. Starting state only — see the standing constraint above; ticket 09 decides whether this changes.
- Every CLI invocation is a **fresh, short-lived process**: load config → run one command → exit. No daemon, no filesystem watcher, no long-running state anywhere today.
- `Note` parsing is a `pulldown-cmark` event stream plus a custom `logos`-based lexer for inline fields/tags/task markers (`src/note/parser.rs`, `src/note/parser/lexer.rs`); **single-pass, no incremental re-parse**.
- **Source spans are almost entirely absent** from the `Note` AST today: links, tags, inline fields, and frontmatter carry no position; only list items/tasks carry a line-only (not byte-offset) position. `src/position.rs` (`ByteOffset`/`SourceLine`) and `src/note/parser/line.rs`'s `ByteTracker` already supply the plumbing to add spans; `pulldown-cmark` already emits byte-offset spans per event today (currently discarded).
- `FileIndex` (`src/index/entry.rs`) is an **immutable, single-owned snapshot**, persisted across three `redb` tables (`FILES`/`NOTES`/`LINKS`, no raw text, no spans), refreshed only via a manual, single-threaded, whole-tree mtime/size diff (`src/index/delta.rs`) — **no filesystem watching exists**.
- `QueryService`/`QuerySet` already expect `Arc<FileIndex>` at the call boundary; query parsing is hand-rolled recursive-descent over `logos`, **`miette` is already fully span-aware** for query diagnostics (`QuerySyntaxError`, `src/query/error.rs:134`) — the strongest existing precedent for LSP-diagnostic-shaped errors in the codebase.
- `SchemaService` is a load-once, in-memory-cached registry (Kahn's-topo-sort `extends` inheritance); **no runtime field-value validator exists** — schema validation only happens when schema *definitions* are parsed, never against Note content.
- Template rendering is **inherently interactive and unsafe to execute for analysis**: minijinja helpers (`ui.*`) synchronously block on live `DialogProvider` I/O mid-render (No-Declaration Format); there is **no static-analysis capability** today (no code path lists a template's referenced helpers/variables without fully executing it) and **no root-template AST caching** (every render re-parses).
- **rumdl already ships its own LSP** (`rumdl server`) with diagnostics, code actions, formatting, fenced-code-block language completion, and file-path/heading-anchor **link completion plus hover/definition/references/rename** for Markdown links, plus its own document/workspace symbol outline — with `enableLinkCompletions` / `enableLinkNavigation` / **`enableSymbols`** settings *explicitly documented* for ceding link intelligence and the heading outline to "another language server (for example a PKM/notes LSP)" (see [rumdl-boundary research](research/rumdl-boundary.md)). Wikilinks are **permanently, unconditionally out of rumdl's link-checking scope by design** ("they name a vault entry rather than a path... the tool that renders them resolves the name itself") — zero overlap to resolve there. rumdl's link-*diagnostics* (`MD057`/`MD051`) are **not** gated by those LSP settings, only by separate lint-rule config.
- **The Rust LSP framework landscape has two separate axes, not one** — see [Rust LSP framework crate research (corrected 2026-09-03)](research/rust-lsp-framework-crates.md): on runtime demands, `tower-lsp-server`/`async-lsp` require an async runtime end-to-end and cancel `$/cancelRequest` by dropping a `Future` (which does not interrupt `spawn_blocking`'d synchronous work if the core stays sync), while `lsp-server`+`lsp-types` (the pair rust-analyzer uses) is a minimal synchronous crossbeam-channel API with fully manual cancellation and no async requirement. On ecosystem adoption, `tower-lsp-server` (the actively-maintained `tower-lsp-community` fork, not the abandoned original `tower-lsp`) is the current de facto standard and most-recommended choice across 2025/2026 tutorials and community discussion — `lsp-server`'s low-level manual-everything shape is what rust-analyzer specifically chose for its own unusual needs (it also built its own incremental query engine), not evidence it's the broader default. Both axes are real input for ticket 09; the first draft of this research over-weighted the runtime-demands axis and under-reported the ecosystem-adoption axis, which is now corrected.
- **rust-analyzer's Host/Snapshot split is a proven, real-world instance of the map's prior hypothesis** — see [rust-analyzer precedent research](research/rust-analyzer-precedent.md): `AnalysisHost` (mutable, transactional `apply_change`) / `Analysis` (immutable, cheaply-cloned snapshot, lock-free concurrent reads) enables "parse-once/project-many"; its VFS treats open editor buffers as the sole source of truth for their own content (files are opaque IDs, no disk IO for already-open files) — directly reusable for the live-buffer-vs-filesystem decision regardless of whether Traces adopts salsa-style full incrementality.

## Decisions so far

- [Research: Markdown Oxide capabilities & architecture](issues/01-research-markdown-oxide.md) — regex-only/no-AST, `tower-lsp`+`tokio`+`rayon`, in-memory only, ambiguity deferred to client, tag rename uses hierarchical prefix match but goto-definition uses exact match only; filesystem-watch triggers a full vault rebuild that overrides unsaved buffers (an anti-pattern to avoid). [Full findings](research/markdown-oxide.md).
- [Research: Marksman capabilities & architecture](issues/02-research-marksman.md) — F#/Markdig, actor-model concurrency, full re-parse per edit with incremental workspace-index-only updates; wikilink resolution (title vs filename) is user-configurable; documented "duplicate heading" diagnostic doesn't actually exist standalone in source. [Full findings](research/marksman.md).
- [Research: rumdl capability boundary and coexistence hooks](issues/03-research-rumdl-boundary.md) — three-setting coexistence contract (`enableLinkCompletions`/`enableLinkNavigation`/`enableSymbols`); wikilinks permanently out of scope by design; link diagnostics not gated by those settings; zero formatting overlap. [Full findings](research/rumdl-boundary.md).
- [Research: zk capabilities & architecture](issues/04-research-zk.md) — strictly single-root Notebook, no daily-note special-casing (composed from template groups + date placeholders), flat tag model with glob-simulated hierarchy, SQLite-backed incremental diff-indexing synced to unsaved buffers. [Full findings](research/zk.md).
- [Research: Microsoft markdown-language-service/server generic baseline](issues/05-research-ms-markdown-language-service.md) — canonical generic-Markdown capability bar (folding/selection-ranges/symbols/links/hover/definition/references/rename/completion/diagnostics) with semantic tokens and CodeLens both deliberately absent; clean protocol-agnostic-library-vs-LSP-adapter split; zero wikilink/PKM support; UTF-16 positions only. [Full findings](research/ms-markdown-language-service.md).
- [Research: rust-analyzer host/snapshot architecture precedent](issues/06-research-rust-analyzer-precedent.md) — Host/Snapshot split confirmed as a real, load-bearing pattern; salsa's core lesson (isolate local/volatile from global/stable state) is separable from adopting salsa itself; VFS/open-buffer-as-truth pattern is directly reusable; "parsing must never fail" invariant matters for Note parsing and template static analysis alike. [Full findings](research/rust-analyzer-precedent.md).
- [Research: Rust LSP framework/transport crate landscape](issues/07-research-rust-lsp-framework-crates.md) — two-axis finding, corrected 2026-09-03: on runtime demands, `tower-lsp-server`/`async-lsp` require an async runtime end-to-end and their automatic `$/cancelRequest` handling (dropping a `Future`) doesn't interrupt synchronous `spawn_blocking`'d work, while `lsp-server`+`lsp-types` is a minimal synchronous crossbeam-channel API with fully manual cancellation and zero async requirement; on ecosystem adoption, `tower-lsp-server` is the current de facto standard/most-recommended choice in the wider Rust LSP community, not `lsp-server` (rust-analyzer's own pick, for its own unusual reasons). Both axes are input for ticket 09's runtime-model decision; neither alone picks a winner. [Full findings](research/rust-lsp-framework-crates.md).
- [Research: Obsidian Dataview/Templater/Metadata Menu/obsidian-tasks parity](issues/08-research-dataview-templater-metadatamenu-parity.md) — none of the four provide real LSP-shaped intelligence (completion-popup precedent only, zero diagnostics/hover/definition precedent); Templater's `tp.*` member-completion and Metadata Menu's `fileClass`-scoped value-completion are the closest structural precedents for tickets 22 and 20 respectively. [Full findings](research/dataview-templater-metadatamenu-parity.md).
- [Research: performant Rust LSP runtime models beyond rust-analyzer](issues/35-research-performant-rust-lsp-runtime-models.md) — fired mid-grilling-session on ticket 09 after user pushback that rust-analyzer alone was too thin a precedent. Across `ty`, `ruff server`, Biome, and Taplo, zero precedent exists for making the core analysis engine itself `async fn`; the real split is fully-synchronous end-to-end (`ty`/`ruff server`, no non-trivial concurrent I/O beyond request/response) vs `tokio`+`tower-lsp-server` at the transport boundary only with a synchronous core underneath (Biome, chosen specifically because its LSP layer has real concurrent I/O — file-watch events, multi-client sessions). Taplo's hand-rolled async stub is a cautionary tale, not a counterexample — its own maintainer wanted to move toward Biome's shape. [Full findings](research/performant-rust-lsp-runtime-models.md).

## Not yet specified

- **Testing/validation strategy for the finished design** — how the eventual implementation gets checked against LSP-conformance expectations and the product-parity bar (Markdown Oxide's PKM set, the generic baseline from ticket 05) is out of this planning effort's destination (a *settled design*, not a test plan) unless it turns out a design decision is genuinely unresolvable without it. Revisit if a ticket surfaces a concrete need.
- **Depth of CodeLens/code-action integration between an unresolved-link quick-fix and Template instantiation** (e.g. "create this note from a template" acting on a broken `[[link]]`) — depends on both ticket 22 (template intelligence) and ticket 28 (file operations) settling first; too fine-grained to ticket precisely until then.
- **Anything ticket 09 (framework/runtime) or ticket 10 (analysis host) settles that invalidates the ticket graph below** — e.g. if the chosen framework forces a materially different host shape than assumed, several downstream tickets (12, 21, 26, 29, 34) may need to be revised or re-split once resolved. Ticket 09 (LSP framework/transport crate & runtime model) is claimed and in progress (live grilling session, 2026-09-04); ticket 35's research broadened its evidence base beyond rust-analyzer. It remains the frontier's active ticket.
