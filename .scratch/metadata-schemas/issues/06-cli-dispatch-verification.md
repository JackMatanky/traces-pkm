## Agent Brief

**Category:** enhancement
**Summary:** Verify Schema-driven Templates render and write through the real CLI dispatch and trust pipeline.

**Current behavior:**
`traces template` renders Templates from parsed command arguments through the CLI, resolving the trusted project root via the config/trust service and writing output. It has no knowledge of Schemas, File Classes, or the schema namespace — the feature's consumer surfaces exist only in library/test seams from tickets 03–05.

**Desired behavior:**
A Schema-backed Template — one that calls `schema.get(...).field(...)`, consumes `file`-field options, or queries with `query.from_class(...)`/`tasks.from_class(...)` — renders correctly and writes output when run through `traces template` against an isolated trusted project fixture containing `.traces/schemas/*.toml` and Notes with `class:` frontmatter. Structural Schema errors surface through the CLI's existing error presentation rather than panicking.

**Key interfaces:**
- The existing `traces template` command path, unchanged except it now reaches the Schema surfaces.
- Test fixture pattern: `ConfigService::at` with isolated trust stores, `CwdGuard::enter`, trusted project fixture with Templates and Schemas.

**Acceptance criteria:**
- [ ] `traces template` renders a Schema-backed Template on an isolated trusted project fixture and writes the output.
- [ ] The fixture exercises the `schema` namespace, file-field options, and class queries.
- [ ] A structural Schema error surfaces as a CLI render error, not a panic.
- [ ] Tests use the existing CLI dispatch pattern (isolated trust stores, `CwdGuard::enter`, trusted fixture).

**Out of scope:**
- New CLI commands (a Schema authoring/validation command is explicitly out of scope for the feature).
- A file watcher/daemon.
- JSON output.
