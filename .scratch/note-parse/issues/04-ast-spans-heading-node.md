## Answer

**Decision: a single `pub(crate)` generic wrapper, `Spanned<T> { value: T, span: Range<ByteOffset> }` — span is mandatory, never `Option` — used for `Note::outlinks()`'s element type, a new body-tags-with-position accessor, and inline-field entries. `Tag` and `Link` themselves are untouched: no new field, no derive surgery. `Heading` is its own concrete `{ level: u8, span: Range<ByteOffset> }` struct (no wrapper, nothing to unify with).**

This supersedes an earlier draft of this Answer that put an `Option<Range<ByteOffset>>` field directly on `Tag`/`Link` to avoid changing `Note::outlinks()`'s and `Note::tags()`'s public return types. That constraint doesn't hold: this crate is `version = "0.1.0"`, `traces-pkm` is a personal application (`src/main.rs` binary, no `crates.io` publication), and CodeGraph confirms `Link::new` and its accessors are already `pub(crate)` — nothing outside the crate can construct or inspect a `Link` today regardless of `Note::outlinks()`'s element type. There is no external caller to protect. Re-deciding on pure design merit below.

**Rationale:**

1. **`Tag` and `Link` are reused as plain values in non-positional contexts; `Spanned<T>` keeps that reuse clean instead of retrofitting position onto it.** CodeGraph confirms `Tag` is constructed and compared in `TaskConfig::tag_filters()`, `ListItem.tags`, and — since ticket 03 — frontmatter-sourced tags merged into `Note.tags()` with no body occurrence at all; `Link` backs `NoteFieldValue::Link` for frontmatter/inline scalar values with no body position. None of these are "an AST occurrence missing its span" (which `Option` would model correctly) — they're a different *kind* of thing: a bare value with no position concept at all. Wrapping only the AST-occurrence use sites in `Spanned<T>` keeps `Tag`/`Link` exactly as they are everywhere else; a shared value type never gains a field that's meaningless in 90% of its uses.
2. **A mandatory span beats `Option<Range<ByteOffset>>` wherever every element genuinely has one.** `Note::outlinks()` is populated only from body Markdown/wikilink syntax — CodeGraph shows its only producer is the parser's link-collection step, 5 total callers, none frontmatter-related. Every outlink has a real span, so `Spanned<Link>` (mandatory) is strictly more precise than `Link` with an `Option` span nobody would ever see as `None` in that collection — the type system should say "always present," not "maybe."
3. **One generic wrapper replaces three bespoke shapes, and gets written once.** The previous draft needed manual `PartialEq`/`Eq`/`Hash`/`Ord` on `Tag` *and* `Link` separately (both currently `#[derive(...)]`; `std::ops::Range<T>` implements neither `Eq`, `Hash`, nor `Ord` for any `T`, so a `Range`-typed field forces manual impls regardless of the `Option`/mandatory question) plus a third, differently-shaped pairing for inline-field entries. A single `impl<T: PartialEq> PartialEq for Spanned<T>` (compare `.value` only, ignore `.span`) — and `Eq`/`Hash`/`Ord` the same way where actually exercised — covers all three uses (`Spanned<Link>`, `Spanned<Tag>`, `Spanned<NoteFieldValue>`) from one place. Three concrete instantiations clears this codebase's own Rule-of-Three bar (the standard this repo already applies — see ticket 11 §5's `TextBuffer` rejection at *two* call sites); the earlier draft under-counted the instantiations and rejected the wrapper on a Rule-of-Three call it got backwards.
4. **`Note.tags()` — ticket 03's just-landed unification — is left completely alone.** `Note.tags() -> &[Tag]` mixes body- and frontmatter-sourced tags by ticket 03's explicit design (the unification is the point of that ticket: one flat list for `#tag` matching and the redb tag-index axes). That collection *inherently* has mixed positional provenance and can't be uniformly `Spanned` without `Option` creeping back in for exactly that one case. Splitting it back into separate body/frontmatter collections would undo ticket 03's unification — a real regression, not a style choice. Instead, this ticket adds a **new**, additive accessor scoped to body-parsed tags only (every element spanned, no `Option`), and leaves `tags()` byte-for-byte as ticket 03 built it. The parser already segregates body tags from frontmatter tags before merging them for `with_tags` (ticket 03's own construction path), so the new accessor's data is already available at the right point in the pipeline — no re-derivation needed.
5. **Inline-field entries need position per-entry, not per-value-type**, because a scalar entry (`Priority:: 3`) has nowhere to attach a `Link`-shaped span field and reusing `NoteFieldValue::Link`'s span would only cover `NoteFieldValue::Link` entries. `Spanned<NoteFieldValue>` pairs the whole entry with its occurrence span uniformly across every `NoteFieldValue` variant. `Note.inline_fields` is confirmed body/list-item-only (`Frontmatter` is a separate `Note` field, never merged in), so every entry has a real span — mandatory, no `Option`, consistent with point 2. CodeGraph shows 24 crate-internal callers of `inline_fields()` (`pub(crate)`) that will need to route through `.value()`; real but contained, mechanical, no external break.
6. **`Heading` carries `level` and `span`, not text.** Ticket 11 §1 lists `Heading` among the span-bearing additions; §2 fixes the shape at "flat list, `level: u8`," naming no text-consuming feature yet (heading-reference/symbols work is explicitly out of scope here). `level` is cached as a typed field because it isn't cheaply re-derivable from a raw slice without re-parsing (ATX `#`/`##` vs. Setext `===`/`---`); heading text, if a later consumer needs it, is one slice away via `span`. `Heading` doesn't need `Spanned<T>` — it's a new type with no other reuse to protect, so `{ level, span }` as its own struct is more direct than wrapping a bare `u8`.

**Guidance for implementation:**

- `Spanned<T> { value: T, span: Range<ByteOffset> }` lives in `src/position.rs`, alongside `ByteOffset`/`SourceLine`/`ByteTracker` — that module's own doc comment scopes it as "source-position primitives... shared across text-parsing domains," and `Spanned<T>` depends only on `ByteOffset` from that module, nothing from `note::`. `pub(crate)`, with `value()`/`into_value()`/`span()` accessors (explicit methods, not `Deref` — matches this codebase's existing accessor style on `Tag`/`Link` rather than introducing `Deref`-based ergonomics for the first time).
- `#[serde(skip, default = "...")]` on `Spanned::span` (`Range<ByteOffset>` has no `Default` impl in std, unlike `Option`, so this needs one small free function, e.g. returning `ByteOffset::default()..ByteOffset::default()` — `ByteOffset` itself does derive `Default` per ticket 01's implementation). One function covers every instantiation.
- `Note::outlinks() -> &[Spanned<Link>]`; `Link` itself unchanged (still bare inside `NoteFieldValue::Link`).
- A new `Note` accessor for body-tag occurrences (name is the implementer's call — e.g. `tag_occurrences()`), returning `&[Spanned<Tag>]`, additive alongside the existing `tags() -> &[Tag]`; `Tag` itself unchanged.
- `Note::inline_fields()`'s value collection becomes `Spanned<NoteFieldValue>` per entry (e.g. `IndexMap<FieldKey, Box<[Spanned<NoteFieldValue>]>>`); update its 24 crate-internal callers (CodeGraph-confirmed: concentrated in `src/index/service.rs`, `src/note/parser.rs`, `src/note/model.rs`) to read through `.value()`.
- New `Heading` type (module: implementer's call, likely alongside `Link`/`Tag` in `src/note/`), added to whatever collection `Note` exposes for document-order elements; no existing type's shape changes to accommodate it.

## Agent Brief

**Category:** enhancement
**Summary:** Add a mandatory-span `Spanned<T>` wrapper used for outlinks, a new body-tag-occurrences view, and inline-field entries; add a flat `Heading` node with level + span. All spans transient, never persisted.

**Current behavior:**
`pulldown-cmark`'s offset iterator emits a byte range per event; only `range.start` is used (to seed `ByteOffset`-based line tracking), `range.end` is discarded. Outgoing links, tags, and inline-field entries carry no position. Headings are not retained in the AST at all — only tags/fields found inside a heading-scoped paragraph are collected; the heading itself leaves no trace. `Note.tags()` returns a flat, unified list mixing body- and frontmatter-sourced tags (landed by the frontmatter-tag-unification work) with no way to distinguish or locate the body-sourced ones.

**Desired behavior:**
1. A `Spanned<T>` value pairs any `T` with its `Range<ByteOffset>` source span (the span type ticket 01 decided: bare range, no further wrapper). Equality, hashing, and ordering on `Spanned<T>` — wherever derived or implemented — compare only the wrapped value, never the span.
2. Outgoing links (`Note::outlinks()`) become spanned: every element carries the byte range of the Markdown/wikilink occurrence it was parsed from. The underlying link-value type itself is unaffected everywhere else it's used (e.g. link-shaped inline/frontmatter field values stay unspanned).
3. A new accessor exposes body-parsed tag occurrences with their spans, additive alongside the existing unified tag list — the existing unified list (which also includes frontmatter-sourced tags with no body position) is unchanged in shape and behavior.
4. Every inline-field entry (`Key:: Value` and its bracketed/parenthesized Dataview variants) carries the byte range of its own occurrence, regardless of the field value's type (scalar, link, list, date, ...).
5. A new flat `Heading` node exists per heading in document order, carrying its level (1–6, matching `pulldown-cmark::HeadingLevel`) and its byte-range span. No parent/child nesting — hierarchy is derivable later on demand by any future consumer.
6. None of these spans are ever written to the redb index store. A note's persisted encode path is unaffected; round-tripping a note through persist/load produces the same result with or without span data present in memory.
7. No behavior changes for any other AST element (lists, tasks, footnotes, callouts, frontmatter, the existing unified tag list) and no existing test assertion needs updating for values that don't inspect spans.

**Key interfaces:**
- A `Spanned<T>` value type (`src/position.rs`, alongside `ByteOffset`/`SourceLine`) pairing `T` with a mandatory `Range<ByteOffset>`; accessors for the wrapped value and the span; equality/hashing/ordering delegate to the wrapped value only.
- `Note::outlinks()`'s element type carries a span (`Spanned<Link>` or equivalent); the link-value type used elsewhere (frontmatter/inline field values) is unaffected.
- A new `Note` accessor exposing body-parsed tag occurrences with spans, distinct from and additive to the existing unified `tags()` accessor.
- `Note`'s inline-field entry storage pairs each `NoteFieldValue` with its own span.
- New `Heading` type: `level` (1–6) and a byte-range span, exposed from `Note` in document order.
- All span data is excluded from the persisted representation (never round-trips through the index store).

**Acceptance criteria:**
- [ ] Outgoing links, body-tag occurrences (via the new accessor), and inline-field entries each carry a source range (start and end) populated during parse, using bare `Range<ByteOffset>` per ticket 01's decision
- [ ] The existing unified `Note::tags()` accessor (body + frontmatter tags) is unchanged in return type and behavior; the new body-tag-occurrences accessor is additive
- [ ] Span-bearing wrapper values compare, hash, and order equal to their wrapped value regardless of span — proven by existing equality-based tests continuing to pass unmodified wherever they compare parser output against freshly constructed values
- [ ] Flat `Heading` node with `level` and span retained in the AST output; existing behaviour for other nodes unchanged
- [ ] Persistence round-trip excludes spans: encode a `Note` with spans present, decode it, confirm no span data survives and no other field is altered — verified by test
- [ ] Parser tests and lint pass (`mise run verify`)

**Out of scope:**
- Frontmatter span storage (deferred to a dedicated design session per ticket 11 §6, which routes it through ticket 19/`noyalib`'s `Spanned<T>` instead — a YAML-position concept, unrelated to this ticket's Markdown-body wrapper of the same name)
- `byte_to_utf16_cu` (LSP-wire concern, ticket 11 §4 already deferred it to `ByteTracker`'s home in `src/position.rs`, not this ticket)
- Any consumer-facing feature: heading-reference resolution, symbol outlines, hover, or anything else that *reads* the new spans — this ticket only lands the data
- `Heading` text/content capture — recoverable later from its span plus source text by whichever ticket needs it
- Changing the unified `Note::tags()` list's contents, ordering, or provenance semantics — that's ticket 03's completed scope
