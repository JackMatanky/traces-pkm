## Answer

**Decision: `Heading { level: u8, text: String, line: SourceLine }` — flat, fully persisted, no span. `Note` gains a `headings` collection with a document-order `headings()` accessor; hierarchy is derived on demand from level + document order and never stored. Plain derives end to end: no `serde(skip)`, no manual `PartialEq`.** Occurrence spans (`Spanned<T>` on links/tags/inline-field entries) left this ticket: the original design's `#[serde(skip)]` plus a "store-loaded spans decode to 0..0" doc invariant was withdrawn as a type-system lie, and the replacement question (persist spans vs model their absence with `Option`) is recorded as md-pkm-lsp research ticket 40 and grilling ticket 41.

**Rationale:**

1. **Flat with derived hierarchy — ticket 11 §2, unchanged.** Every studied peer (Marksman, Markdown Oxide, Microsoft's generic-Markdown service) stores headings as a flat list with a level field and derives the tree with a stack algorithm on demand; no peer builds parent/child links at parse time. `level` + document order fully determine the tree, so stored `parent`/`depth` fields would be redundant state that can only drift from the truth — and with no consumer yet in scope (symbols and heading references are explicitly out of scope here), that state would be speculative on top of redundant.
2. **`line`, not a span: it is the persisted, redb-safe form of "where".** Ticket 11 §8 keeps spans out of redb (cheap to recompute, invalidated by every edit, a format bump for data no store-side query serves), but a heading's position must survive persistence for the same reason list items' does: `ListItem.line: SourceLine` with hand-rolled serde (`src/position.rs:389-409`) is the landed precedent, and `SourceLine` is exactly the primitive that already crosses the store boundary. A `ByteSpan` field on `Heading` would force the very decision this ticket was stripped of: either persist it (needs §8 amended — grilling 41) or `serde(skip)`/`Option` it (the invariant smell that got the previous design withdrawn). Line granularity is also what this ticket's data is for — `[[#anchor]]` resolution and future symbol/outline consumers key on lines — and any future consumer that truly needs bytes can recover them from `line` plus the source text it already holds.
3. **`text` is captured at parse time because it is not recoverable without re-parsing.** The heading's source bytes carry ATX/Setext markers, emphasis and link markup, wikilink pipes; consumers need the markup-stripped string — the same plain-string shape `LinkTarget::AnchorOnly`/`PathWithAnchor` anchors already parse out of `[[#Heading]]`. Collecting only `Event::Text`/`Event::Code` payloads between `Start(Heading)`/`End(Heading)` does the stripping structurally: markers, inline markup, and raw HTML never arrive as those events. For links the same rule yields the **display** text (`[[Page|alias]]` → `alias`), never the source spelling — which is exactly what a future `[[#anchor]]` matcher needs.
4. **Everything persists; nothing is conditional.** `level`/`text`/`line` are parsed content, the same category as tags, outlinks, and list items that already round-trip through the `NOTES` table. Plain derives on all three fields mean no `serde(skip)`, no manual `PartialEq`, and no decoded-vs-encoded mismatch for tests to dance around. The `Note` struct gains one field; pre-release, that is a routine full rebuild, not a migration project — no version byte, no format handling (explicit project direction: migration mechanics are a non-concern before release).
5. **Why spans are no longer here.** The previous design paired a *mandatory* `span: ByteSpan` with `#[serde(skip)]`, so every store-loaded note carried structurally present but semantically dead `0..0` spans, with correctness resting on a doc comment ("never trust a loaded span"). That is a prose invariant that rots silently: a caller reading the type sees "always present" and has no way to know it lies after a load. Withdrawing it (user direction, this session) leaves a genuinely open question that needs evidence this ticket does not have — persist spans (option B) or model their absence honestly with `Option` (option C). That lives in md-pkm-lsp research ticket 40 and grilling ticket 41; ticket 11 §8 stands untouched meanwhile.

**Guidance for implementation:**

- `Heading` lives in `src/note/` (implementer's call: a new `heading.rs` beside `links.rs`, or inside `model.rs` next to `Note`), `#[derive(Clone, Debug, Eq, PartialEq, Serialize, Deserialize)]` — the `Note`/`ListItem` derive set plus `Eq`, which is free here (no floats) — and no manual impls of any kind.
- Parser: split the merged `Start(Paragraph | Heading)` / `End(Paragraph | Heading)` arm at `src/note/parser.rs:293-303`. On `Start(CmarkTag::Heading { level, .. })`, in addition to the existing `start_text_block()`, record `line_index.line_at(span.start())` and the level (convert `pulldown_cmark::HeadingLevel` with a `match` — `clippy::as_conversions` is warned workspace-wide at `Cargo.toml:227`). While the heading is open, append `Event::Text`/`Event::Code` payloads to a dedicated heading buffer and render `Event::SoftBreak`/`Event::HardBreak` as one space — alongside, not instead of, the existing `push_text`/`inline_code` routing, which must keep feeding tags and fields inside headings (`extracts_a_tag_from_heading_text` and `extracts_a_bare_field_from_heading_text` are the guard-rail tests). On `End(TagEnd::Heading(_))`, push `Heading { level, text, line }` to the collection, flush the buffer, then run `end_text_block()` as today.
- `Note` (`src/note/model.rs`): new `headings: Box<[Heading]>` field, added as a **seventh parameter to `Note::new`** — that constructor is `Note`'s only construction path and already carries `#[expect(clippy::too_many_arguments)]` (`model.rs:36-39`) precisely to take every component; there are no `with_*` builders on `Note` (those are `ListItem`-only, `src/note/lists.rs:84-141`). Mechanical churn: 14 test call sites in `model.rs` plus `into_note` (`src/note/parser.rs:353-369`) pass an empty collection. Add `pub fn headings(&self) -> &[Heading]` beside `lists()`/`outlinks()`.
- Round-trip test: extend `preserves_populated_collections_across_postcard_roundtrip` (`src/note/model.rs:548`) with a heading, or add a sibling case in its `mod serialization`, asserting `level`/`text`/`line` survive and the note still compares equal.
- The binding test matrix is the "Parser tests cover this matrix" acceptance criterion above — implement it there rather than restating it here.

## Agent Brief

**Category:** enhancement
**Summary:** Add a flat `Heading { level, text, line }` node collected on `Note` in document order; `text` is markup-stripped plain text, `line` resolves through the landed `LineIndex`; all three fields persist with plain derives. No spans anywhere — the occurrence-span half of this ticket moved to md-pkm-lsp research ticket 40 / grilling ticket 41.

**Current behavior:**
`pulldown-cmark`'s offset iterator hands every event's byte span to `handle_event` (`src/note/parser.rs:115`, `:274`), but headings leave no trace: `Start(Heading)`/`End(Heading)` share the paragraph arm (`:293-303`) solely so `start_text_block`/`end_text_block` route heading text through the buffers that collect tags and inline fields — the heading itself is dropped. `ParserContext` already owns `line_index: LineIndex` (`:224`) used for list-item line tracking.

1. Every heading yields `Heading { level: u8 (1–6), text: String, line: SourceLine }`, appended in document order; hierarchy stays out of the AST — it is derivable from level + document order.

3. `line` comes from the `Start(Heading)` event span via `line_index.line_at(span.start())`.
4. `level`/`text`/`line` all persist through postcard like tags/outlinks/list items; the pre-release rebuild absorbs the `Note` layout change.
5. No behaviour change for any other node; tags and fields inside headings keep collecting; `mise run verify` passes.

**Key interfaces:**
- `Heading { level: u8, text: String, line: SourceLine }` with derived `Clone, Debug, Eq, PartialEq, Serialize, Deserialize`.
- `Note::headings() -> &[Heading]` in document order; `headings` is a seventh `Note::new` parameter (the constructor already expects `too_many_arguments`).
- No span type, no `Option`, no `serde(skip)`, no manual equality anywhere in this ticket.

## Implementation notes (heading-node worktree)

Implemented in `73800a01`; follow-up refactors in `6139973d` and `89a879d6`. The checklist and Agent Brief above record the original request; the implementation now lives in these files:

- `src/note/heading.rs`: `Heading` has private `level: u8`, `text: String`, and `line: SourceLine` fields, with public read-only `level() -> u8`, `text() -> &str`, and `line() -> SourceLine` accessors. It derives `Clone`, `Debug`, `Eq`, `PartialEq`, `Deserialize`, and `Serialize`. Construction and text accumulation are crate-private parser operations. The type remains publicly re-exported through `src/note/mod.rs` and `src/lib.rs`.
- `src/note/model.rs`: `Note` stores `Box<[Heading]>` and exposes `headings() -> &[Heading]`; the collection is the seventh component of the internal `Note::new` constructor. The existing populated postcard round-trip test includes a heading and checks the decoded note against the original. Existing serialized note indexes must be rebuilt after this pre-release layout change; no format migration was introduced.
- `src/note/parser.rs`: metadata uses its existing event stream, while a second traversal collects headings with math parsing enabled. On heading start, map the pulldown level to 1–6 and resolve the start line with `LineIndex`; accumulate text/code event display payloads and spaces for soft/hard breaks; append the completed heading on heading end. Link and wikilink display text is retained without source markup, while markup-only headings still produce empty-text nodes. The separate traversal preserves outlinks inside math-like text, and footnote source spelling remains available to metadata/list scanning without entering heading display text.
- Parser tests cover ATX levels 1–6 and order, multiline Setext text and first source line, inline markup and link/wikilink display text, empty headings (including math, HTML, and footnotes), and nested blockquote/list headings with metadata. Regression tests cover math/footnote text in list items and outlinks within math-delimited heading text.

Verification after the private-field follow-up: `mise run verify` passed (3,135 tests across four binaries and 71 doctests); `mise run doc -- --all-features` passed. The module-split follow-up also passed `mise run modules:orphans` (no orphans). A public-API smoke example exercised parsing and `Note::headings()` before the private-field follow-up; the parser tests exercise the current accessor API.
