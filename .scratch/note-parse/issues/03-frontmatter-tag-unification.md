## Answer

**Decision: the configured frontmatter tag key is the sole source; `tag`/`keywords` are not read as fallbacks.**

**Rationale:**

1. `FrontmatterConfig`'s existing title/aliases pattern is single-key with no
   fallback chain: `title_name()`/`aliases_name()` each resolve exactly one
   configured `FieldName`, defaulting to `"title"`/`"aliases"`. A tags
   accessor that also silently scans `tag` and `keywords` behind the
   configured key would be the only frontmatter-config accessor in the
   codebase with implicit fallback semantics — a user who points
   `tags_name` at `"categories"` would still see stray values leak in from
   an unrelated `tag`/`keywords` key they never configured.
2. md-pkm-lsp ticket 16 §5's `tags`/`tag`/`keywords` list predates this
   ticket's explicit "same pattern as `title_name`/`aliases_name`"
   instruction. This ticket's spec text supersedes ticket 16's broader list
   for the frontmatter-tag-*key* question specifically; ticket 16 remains
   authoritative for the LSP completion/rename/reference semantics it
   defines elsewhere (out of scope here — see below).
3. If a project's frontmatter genuinely spreads tag data across more than
   one key, the single-key config is not a functional gap: point
   `tags_name` at whichever key is actually used. Multi-key aggregation
   would need its own merge/precedence rule and is unrequested — YAGNI
   until asked for.

This closes the "Key-precedence question vs ticket 16's `tags`/`tag`/
`keywords` list" acceptance criterion.

## Agent Brief

**Category:** bug
**Summary:** Frontmatter tag values are ignored by tag filtering; unify them
into `Note.tags()` via a new configurable frontmatter key name.

**Current behavior:**
`Note.tags()` is populated only from `#tag` tokens found in Markdown body
text and list items. `src/note/CONTEXT.md` documents Tag as "extracted from
body text and frontmatter", but the parser never reads frontmatter for
tags — a frontmatter `tags:` (or similarly named) key lands only as an
ordinary `Frontmatter` field. Because `#tag` source-expression matching, the
`tags` query field, and the tag-based redb index axes all read
`Note.tags()`, none of them see frontmatter-declared tags today: `#book`
won't match a note whose only `#book` tag lives in `tags: [book]`
frontmatter, and that note is absent from the persisted tag index.

`FrontmatterConfig` already exposes single, non-fallback key-name accessors
for other frontmatter roles (`title_name()`, `aliases_name()`, each backed
by one `FieldName`, defaulting to a fixed key string) — there is no
accessor for a tags key yet.

**Desired behavior:**
1. `FrontmatterConfig` gains a tags-key accessor following the exact
   `title_name`/`aliases_name` shape: one `FieldName`-backed field, a public
   getter returning `&str`, a `"tags"` default, and a raw-config
   `Option<String>` input resolved the same way `title`/`aliases` are
   (fallible `FieldName` validation; an invalid configured key fails config
   loading the same way an invalid `title`/`aliases` key does today).
2. During parsing, the note's frontmatter is inspected under the configured
   key. The key's value is read using the same scalar/list flattening
   already used elsewhere for multi-valued frontmatter fields, so:
   - a list value (`tags: [a, b]`, or a YAML block list) yields one
     candidate per element,
   - a scalar string (`tag: a`) yields one candidate,
   - a comma-separated scalar string (`tags: a, b`) yields one candidate
     per comma-separated, whitespace-trimmed segment.
   Each candidate has any leading `#` trimmed, then is validated through the
   same tag-parsing rules body tags already use. A candidate that fails tag
   validation (empty, invalid leading character, disallowed body character)
   is silently skipped rather than failing the note's parse — consistent
   with how other frontmatter key lookups in this codebase drop entries
   that fail their target type's validation.
3. Frontmatter-sourced tags are merged into `Note.tags()` alongside
   body-sourced tags. (Relative order between the two groups is not
   acceptance-tested here; document whichever order the implementation
   naturally produces.)
4. No other layer needs code changes: `#tag` source-expression matching,
   the page-level `tags` query field, and the tag redb index axes already
   derive entirely from `Note.tags()`, so they pick up frontmatter tags
   automatically once (1)-(3) land.

**Key interfaces:**
- `FrontmatterConfig`: new key-name accessor (e.g. `tags_name() -> &str`),
  defaulting to `"tags"`, built the same way as `title_name`/`aliases_name`
  (owning a `FieldName`, validated via `TryFrom` on the raw config struct,
  same invalid-key error variant those two already use).
- Note parsing: a step that reads the frontmatter value at the configured
  tags key and extends the tag collection that already feeds
  `Note::with_tags`, alongside the existing body-tag collection.
- `Tag`: reused unmodified — frontmatter candidates must pass through the
  same parse/validation as body tags (`#`-prefixed,
  `[a-zA-Z][a-zA-Z0-9_/]*`-body format).

**Acceptance criteria:**
- [x] `FrontmatterConfig` exposes a tags-key accessor defaulting to
      `"tags"`, resolvable from raw config the same way `title`/`aliases`
      are, rejecting an invalid configured key the same way `title`/
      `aliases` do
- [x] A note with frontmatter `tags: [a, b]` (or `tags:\n  - a\n  - b`)
      produces `#a` and `#b` in `Note.tags()`
- [x] A note with frontmatter `tags: a` (bare scalar) produces `#a` in
      `Note.tags()`
- [x] A note with frontmatter `tags: a, b` (comma-separated scalar)
      produces `#a` and `#b` in `Note.tags()`
- [x] A frontmatter tag value written with a leading `#` (e.g.
      `tags: [#a]`) normalizes to `#a`, not `##a`
- [x] A frontmatter tag value that fails tag validation (empty string,
      leading digit, disallowed character) is dropped rather than
      surfacing a parse error or corrupting the rest of the note's
      frontmatter
- [x] Configuring a non-default tags key (e.g. `tags_name = "categories"`)
      reads from that key instead of `"tags"`; an unconfigured `tag`/
      `keywords` key is *not* read as a fallback
- [x] A note carrying both a frontmatter tag and a body `#tag` has both
      present in `Note.tags()`
- [x] `#tag` source-expression matching (`query.from("#a")`) matches a note
      whose only `#a` tag is frontmatter-sourced
- [x] The redb tag index (path-by-tag and tag-by-path lookups) contains
      entries for frontmatter-sourced tags after an index write
- [x] Existing body-tag and inline-field/frontmatter-field tests are
      unaffected (no assertion changes to currently-passing tag or field
      extraction behavior)
- [x] Project lint and test tasks pass (`mise run verify`)

**Out of scope:**
- Frontmatter tag *spans* (byte ranges for individual frontmatter tag
  values) — explicitly deferred with the frontmatter-span design session
  per this ticket's stated scope
- Reading `tag`/`keywords` as fallback keys — see the "Key precedence"
  Answer above; only the configured key is read
- List-row/task-row `tags` (the per-`ListItem` tag field used by
  `list.tags`/`tasks`-mode queries) — that stays scoped to a list item's
  own text-scanned tags. Frontmatter tags are document-level with no
  natural single list item to attach to, so list/task-row tag resolution
  is unchanged by this ticket
- LSP tag completion, rename, references, or any other md-pkm-lsp ticket 16
  capability — this ticket is data-model unification only
