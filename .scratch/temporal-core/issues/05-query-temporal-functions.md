# 05: Query temporal functions

**What to build:** The query language speaks Dataview's headline idiom: `date + duration`, `date - duration`, `date - date` yields a duration, and `date_add` / `date_diff` / `date_component` answer period-bucketing questions — all as registry entries, no new operators or grammar. Demo contract: a filter expression that adds `dur("1 month")` to a note's date and compares the result against another date returns the same answer as the template engine would.

**Blocked by:** 03 **and** 04 (needs the calendar owner — 03 — behind a stable recognition/classification interface — 04; encoded chain 03 → 04 → 05; the original header named only 04 and buried 03 as a parenthetical, which review found to be the wrong shape because the dependency is a transitive *seam*, not just a schedule).

Skills: `rust-integration-testing`, `rust-skills`. Rules: `FilterFunction` registry = open/closed (no grammar changes), `conv-tryfrom-fallible` for `date_component` extraction; edge strategies named per workflow. Design record: `../review.md` §3 (B17/B18/B24), §9 (S3); spec stories 1–5.

**Review amendments (2026-10-05 adversarial rust-design pass; source: `../review.md` §11):**

- [ ] **OPEN DECISION (X1) — this ticket is undeliverable as written until resolved.** Spec line 75 locks query features to `FilterFunction` registry entries "never new operators or grammar", and the three stories this ticket implements require exactly the grammar the lock forbids: `FilterFunction` is a one-variant predicate enum (`Contains`, `src/query/grammar/filter.rs:110-121`, variant at `:116`) whose argument parser takes literals only, so `dur("1 month")` inside a filter is a **syntax error today** (`grep -c "dur(" src/query/` → 0; no value-expression node exists), `date − date` must yield a *value* to feed a comparison (nothing can carry one), and `date_add(...)` results cannot be comparison operands for the same reason. Items 1–3 above (B17/B18) are therefore not registry entries — they need a function-as-value expression surface, a two-field-arg convention, and an `op` on function results. **Decision required, with evidence, before scheduling:** (i) amend spec line 75 to name that minimal surface (then this ticket delivers stories 1–3 verbatim), or (ii) restate stories 1–3 as function-only predicates (`date_add`/`date_diff`/`date_component` as filters — item 4 stays deliverable today) and amend the demo contract (line 3) to a shape the current grammar can parse. Do not pick silently during implementation; both outcomes change spec and the demo contract above.
- [ ] **OPEN DECISION (X7) — does this ticket wire multi-part `apply`?** Spec decision 12 ("multi-part dates take an applied `Vec<(DurationUnit, i64)>`") has **no live consumer**: `DateTimeValue::apply`/`DateValue::apply` are `expect(dead_code)` (the six-site census in ticket 09), and nothing in this ticket's items exercises multi-part application. If no consumer will exist after 05–07, ticket 09's deletion test tension becomes a mandate to delete them (breaking spec decision 12's premise) unless 09 records an exemption. Decision: does `date_add` with a compound duration land here (giving `apply` its consumer), or does 09 get an explicit keep-with-rationale exemption? Either answer is fine — but 09 cannot produce "wire or delete" without it. *(Related: `DurationValue::parts` and `from_seconds` sit in the same bucket.)*
- [ ] **(entry point, for §11 D1 sequencing)** When items 1–3 expose arithmetic to queries, route it through the calendar owner's public entry (the `DatePoint`/`DateValue::shift` shape §11 D1 proposes) rather than through the engine's `date_shift_unit` — the engine becomes a *caller* of that entry, not the owner. If D1 is not yet landed when this ticket starts (it is deliberately unassigned; see ticket 04's ordering note), pin this: new query-side call sites must not add a sixth home for the frame policy (`engine/date.rs:469-491` policy copy).
