# Spec: Date & Duration Cluster — Deepening and Parity

Status: ready-for-agent

> **Historical note (2026-10-05, §12.3 Q1e):** the Problem Statement below is the *as-written* record of why this effort started. Several of its items have since been fixed by tickets 01/03 — the silent panics (N1), the dead fixed-magnitude bridge (30-day `month`), and the 301-digit `DurationSeconds: Display` (N19, fixed at `duration.rs:1095`). Treat them as regression-guard context, not current state; current state is the checklist statuses in the tickets.

## Problem Statement

Traces' date/duration layer is the least trustworthy cluster in the codebase. It silently panics on out-of-range durations, its YAML-deserialized dates behave differently from the same dates typed inline (different grammar, different round-trip), the template engine owns the one live calendar implementation while core holds a dead fixed-magnitude bridge (`month` = 30 days), so the two *meanings* of month diverge and `date_add` can visibly do nothing, and a reader can never tell whether "1 month" means 30 days or a calendar month because both meanings are in the code and neither is declared. Meanwhile two citation-backed parity reviews against Dataview and Templater show the query language missing its headline idiom (`date + duration`) and the template layer missing `durationformat` and moment-style formats — the features users copy from those plugins most.

For a vault tool, this is user-facing: a note written in New York silently compares wrong-by-hours against file timestamps and a month-duration query is wrong five days a year; behind the same surface sits a latent public-API defect (`DurationSeconds: Display` renders a 301-digit number, though it has no non-test caller yet — a test-demonstrated edge, not a user-facing one). The cluster also can't grow safely — every parity feature currently requires editing core match statements, so the open/closed property the rest of the codebase enjoys (registry entries) is absent exactly where the divergence risk is highest.

## Solution

Make `date.rs`/`duration.rs` a set of deep modules with declared, single-owner seams, then land the parity gaps as registry entries on top:

- **One calendar owner:** shift/diff/apply live in the date module; the template engine and (future) query functions become thin adapters over it. Adding a unit means editing one table, not four matches.
- **One declared duration regime:** identity is seconds (fixed ratios, named as such); application of day/week/month/year parts to dates is calendar (local wall-clock frame), left-to-right — the Luxon-style "equal values, different shifts" behavior is declared, pinned by test, and documented instead of hidden in an engine `match`.
- **One recognition entry per domain:** a `classify` trichotomy (`None` = cheap shape gate, `Some(Ok/Err)`) retires the guard-protocol functions that two call sites have already forgotten to honor.
- **Precision lives at the recognition layer**, so `YYYY-MM` survives arithmetic and the engine deletes the shadow type it had to invent.
- **Deserialization funnels through the same parser as inline input**, making the documented funnel claim true.
- **Naive datetimes mean local time** (both plugins' behavior), stored as UTC, with a decided DST policy (ambiguous → earliest, true gap → shift forward, tz-data/OS lookup failure → error) enforced by a single gap-verified resolver.
- **Parity arrives as registry entries:** query temporal functions in the `FilterFunction` registry, `durationformat` and a scoped moment→strftime translator as template filters, shorthands as engine adapters over the calendar owner.

Everything is verified through three existing seams — value-type interfaces (unit), the query `FilterFunction` registry (integration), and template filters (integration) — with no new seams.

## User Stories

1. As a query author, I want to write `date + duration` and `date - duration` in filter expressions (Dataview's headline idiom), so that I don't have to compute offsets by hand.
2. As a query author, I want `date - date` to yield a duration, so that I can ask "how old is this note" in one expression.
3. As a query author, I want duration arithmetic (`duration + duration`, `duration * number`), so that I can build derived offsets.
4. As a query author, I want `date_component(date, "year"|"month"|"day"|...)` plus start/end-of-week/month/year helpers, so that I can bucket notes into periods (week buckets per Dataview minus the `.week` footgun).
5. As a query author, I want `date_add`/`date_diff` to accept **any** documented unit spelling (weeks, ms, abbreviations), so that the docs never lie about what parses.
6. As a query author, I want `file.day` available on notes, so that day-bucketed views work like Dataview's.
7. As a template author, I want `durationformat` producing human-readable durations ("3 days, 4 hours"), so that output reads naturally.
8. As a template author, I want common moment tokens (`YYYY MM DD HH mm ss`, `Do`/`S` ordinals, `dddd`/`ddd`/`MMM`/`MMMM`, bracket literals like `[Daily]`) accepted in template date formats, so that templates copied from Dataview/Templater render without rewriting.
9. As a template author, I want an unsupported moment token to fail with an error that **names the token**, says the input was treated as moment-dialect, and points at the supported list — so that I know exactly what to fix.
10. As a template author, I want ISO-8601 duration offsets (`P1M`, `P-1M`) accepted on date shorthands like `date.now`, so that Templater recipes work unchanged.
11. As a template author, I want the `weekday(n)` argument form and the `sow`/`eow`/`soy`/`eoy` bucketing shorthands (the other pieces — `tomorrow`/`yesterday`, start/end-of-month, no-arg `weekday` — already exist), so that daily-note workflows are one expression.
12. As a note author, I want a naive datetime in YAML (`2026-07-29 14:30`) interpreted in **my local zone** and stored as UTC, so that my timestamps compare correctly against file times instead of being wrong by my UTC offset.

As a note author in a DST timezone, I want an ambiguous fall-back time to deterministically resolve to the **earliest** occurrence and a spring-forward gap to shift forward, so that ambiguity and DST gaps never make parsing fail (only a tz-data/OS lookup failure does) and results are reproducible.

## Implementation Decisions

**Cluster ownership & architecture**

- The date module owns calendar arithmetic: `shift(base, n, unit)`, `diff(a, b, unit)`, `apply(base, &DurationValue)`. The template engine and query layer become thin adapters over it; the engine's copied shift/diff implementations are deleted. Calendar meaning for day/week/month/year exists **only** behind this owner — no unit method exposes it (one place defines it).
- Query temporal features are `FilterFunction` registry entries for predicates, extended by a **minimal value-expression surface** — and nothing beyond it. **Decided 2026-10-05 (§11 X1, option (i)):** the grammar grows exactly this and no further: field references; literals; registry function calls returning values (their arguments are themselves value expressions — this covers the two-field-arg convention); `+`/`-` on date/duration values (including `date − date` → duration); `*` by a number; and comparison operators whose operands may be any value expression, including function results. No operator precedence beyond left-to-right, no boolean algebra beyond the existing filter combinators, no user-defined functions. Stories 1–3 and ticket 05's demo contract stand as written. Everything outside this fence returns to the lock — never new operators or grammar beyond the enumerated surface.
- The unit registry (parse table) is the single source of unit knowledge; the duration constructor's private ms-ratio table is derived from it. Month/Year omission from magnitude-derived conversion is documented (unsynthesizable from a magnitude).
- `DurationUnit::seconds()` is renamed `fixed_seconds()` (and `seconds_i64` → `fixed_seconds_i64`) so the fixed regime is in the name at every call site.
- Rejected: `Clock`/`TimeZone` traits (one adapter = hypothetical seam; doctrine is data + docs), a `Dialect` trait (the moment translator is a pure function at the template seam), typestate parse builders, merging `DateError`+`DurationError`, `Cow<'a, str>` for the stored raw string (lifetime parameter = interface bloat), locale-configurable first day of week (pinned ISO Monday), a combined date-or-duration mega-classifier (coercion-layer policy stays at coercion seams), **a `DurationValue` type split** (reconfirmed 2026-10-05, §11.5: the grammar mixes calendar and fixed parts inside one value — `1d 2h` — identity is seconds-based per D13 so `1d == 24h` spans any split, `Add` crosses classes, `api-parse-dont-validate` is already satisfied because `parse` is the sole validated constructor, and the parser's complexity-78 score would move wholesale; the class-predicate version of the split is the already-rejected `DurationUnit::class()` one level down), a `Scanner<'a>` type for the duration parse machinery (stateless helpers; ticket 04 collapses the only stateful loops; adjacent no-split already settled), and a private `Frame` trait for `apply`/`shift` (one behavior-varying pair; the public `Shift` trait rejection at review §5.7 covers it — the two frame impls are the real-seam test).

**Duration semantics (decision A2′)**

- `DurationValue` shape: `raw: Box<str>` + `seconds: DurationSeconds` (sole Eq/Ord/Hash identity) + `parts: Option<Box<[(f64, DurationUnit)]>>`. `parts` entries carry the **written** magnitude, signed with the whole-duration sign applied (N15b: `"-1h 30m"` → `[(-1.0, Hour), (-30.0, Minute)]`), so Σ is one plain left-to-right fold. Exactly two filling *behaviors*: one shared text fold reached by `parse` **and** (until ticket 04's `classify` absorbs it) `parse_prefix`, computing `seconds` as a single left-to-right fold over the entries it just read, computed in one statement — and duration arithmetic (below), whose `Some`+`Some` results compute `seconds` as that same fold over the combined entries, so Σ holds bit-exactly by construction; no runtime validation on either.
- `parts` doubles as the regime witness: `Some` containing `Day`/`Week`/`Month`/`Year` ⇒ calendar application; `Some` without ⇒ fixed (sub-day-only parts); `None` (synthesized values) ⇒ fixed. Matched exhaustively as data, no extra enum.
- **Day as calendar application unit (D13):** Identity stays seconds-based (fixed ratios); day joins month/year as a **calendar** application unit, applied left-to-right in written order (chrono's `Days` type exists because `TimeDelta::days(1)` surprises; PostgreSQL documents `+ interval '1 day'` ≠ `+ interval '24 hours'` across DST). So `1d == 24h` as values but may shift differently — the A2′ incoherence extends to days and is pinned by test. Sub-day units (h/min/s/ms) apply as exact durations on the instant.
- **Week is a calendar application unit too (≡ 7 wall-days):** it is not sub-day, and moment (*"adding years, months, weeks, or days…"* — research item 24) and Temporal (weeks require `relativeTo` — item 25) both treat it as calendar; PostgreSQL `interval '1 week'` ≡ `+ 7 days`. The engine applies week as exact seconds today — this clause **deliberately changes that**, preventing `1w` vs `7d` from becoming a new undeclared incoherence the moment day turns calendar. Pin `1w` ≡ `7d` shifting identically and `1w` vs `168h` differently across DST, beside the `1d`/`24h` test. Verify Luxon during implementation (item 23 lists only days/months/years); if Luxon differs, it earns a divergence-register entry.
- **Calendar frame (D12):** calendar application preserves the **local wall clock**: `shift`/`apply` for day/week/month/year units round-trip through the local zone — `DateTime<Utc>` → local naive → chrono `checked_add_months(Months)`/`checked_add_days(Days)` (never fail on DST — naive has no DST) → back to UTC through the single resolver; sub-day units remain exact on the instant. Precedent: Temporal `relativeTo`, Luxon `plus`, PostgreSQL `+ interval '1 day'`/`'1 month'`.
- The Luxon-style incoherence (equal values, different date-shifts — the incoherence now extends to `1d` vs `24h` across DST) is **accepted and declared**: glossary clause + a pinning test that demonstrates it. A1′ (reject `mo`/`y`) and A3′ (shape identity) explicitly rejected — they break pinned cross-spelling equality and the plugins' documented idioms.
- Duration arithmetic: `Add`/`Sub` on `DurationValue` — with **both sides `Some`**, `seconds` is one left-to-right fold over the combined entries (`Sub` = concat with each rhs entry negated), which equals "seconds add" up to float rounding and makes Σ bit-exact by construction (direct `lhs.seconds ± rhs.seconds` would diverge by non-associativity: `1e16s + ("1s 1s")` folds to `1e16`, direct-adds to `1e16+2`); **with either side `None`**, `seconds` adds directly (`Sub` = add of the negated rhs); `parts` concatenate only when **both** sides are `Some`; **either side `None` ⇒ result `None`** — Σ forces it: a half-inherited witness would lie, and the regime then honestly reads `None` ⇒ fixed; `-0.0` normalized (existing `DurationSeconds::normalized`); result `raw` re-synthesized through `from_seconds` (display-only — the witness is never encoded in `raw`); `Mul<f64>` scales the entries (`Some` ⇒ `seconds` = fold of the scaled entries; `None` ⇒ `seconds` scales directly) — and, since `Mul` cannot fail, a non-finite scalar or overflow to ±∞/NaN leaves `seconds` non-finite, **declared** in `DurationValue`'s type docs (its "always finite" claim narrowed to construction paths, mirroring `DurationSeconds`) and rejected by every consuming conversion with the existing `NonFiniteSeconds` error, never panicking; equality remains seconds-only.

**Recognition & precision**

- Each domain gains one entry point: `classify(s) -> Option<Result<Value, Error>>` (`#[must_use]`). Trichotomy: `None` = O(1) shape gate, no allocation (lexer hot path preserved); `Some(Err)` = allocating detail; `Some(Ok)`. This replaces `can_start && parse` call sites, absorbs the coercion-cascade protocol copy, retires the public guard functions to private, merges the duplicated `parse`/`parse_prefix` loops (killing the `"1h 1x"` divergence), and reduces `TextShape` to a caller rather than a fourth recognition fragment.
- A `Precision` enum (`YearMonth` | `Date` | `DateTime`) is hoisted to the recognition layer alongside a recognition-result struct; the engine's private precision/parsed-date/format-precise trio delegates to it and is deleted. Precision never participates in `DateValue` equality. This is also where fractional truncation in arithmetic re-serialization gets fixed — once, behind the hoisted precision. **OPEN (2026-10-05, §11 X8):** neither this spec nor ticket 04 names where the `YearMonth` strftime pattern (`%Y-%m`) lives after the hoist (presumably a method/entry on `Precision`), nor that `date_shift_unit` must recover `wall` from the value once `ParsedDate` is deleted (derivable: `DateValue` → midnight, `DateTimeValue` → `local_wall()`, `YearMonth` → day-1 midnight). Ticket 04 must settle both.
- Format enums gain a `parse_any`-style constructor that owns the cascade loop (currently copied four ways) — adding a recognized shape becomes one variant + list + pattern entry.

**Parsing, formatting, serde**

- **DST policy / local→UTC resolver (D14):** Naive datetime input parses as **local zone → UTC**; date-only input is zone-free; `now`/`today`/file-stat reads use the local clock, storage is always UTC. DST policy: one named resolver owns local→UTC, exhaustively matching `MappedLocalTime::{Single, Ambiguous, None}` — ambiguous → earliest (policy "earliest"; **mechanism 2026-10-05: the manual `local_minus_utc()` comparison at `src/date.rs:1064-1076`, never chrono's `.earliest()` API — chrono's `Ambiguous` pair ordering is platform-dependent and `.earliest()` returns the latest occurrence on unix; see §13 RPT-F1**), true gap → shifted forward by the gap, while `None` caused by a tz-data/OS error surfaces as an error, never a silent shift (gap verified by probing adjacent local times). **Issue (§11 X4, raised 2026-10-05):** `From<DateValue> for DateTimeValue` (`src/date.rs:741-749`) currently violates this absolute wording — on zone failure it silently falls back to UTC midnight (`unwrap_or_else(|_zone_failure| midnight.and_utc())`), and it is reachable from filter equality (`is_equal_to_date` `src/date.rs:681-683`), so `Date == DateTime` would compare at UTC midnight while every other path returns `DateError::LocalZoneLookup`. **Decided 2026-10-05 (§11 X4, option (a)):** keep `From`, with a **declared exception** to the sentence above: on zone-lookup failure this promotion degrades to the neutral UTC frame (the civil date read as UTC — deterministic and shift-free) instead of surfacing `LocalZoneLookup`, because the infallible conversion is consumed by equality, sort-key, and ordering paths that cannot propagate an error, while `TryFrom` would duplicate the same fallback at each of them. The exception is recorded as a divergence-register entry (entry number assigned when the register is written, ticket 08), and the impl's rustdoc must state this spec rationale in place of the "chrono does the same" parity argument, which does not satisfy this line. Every other path still surfaces `LocalZoneLookup`. Its rustdoc cites Temporal `'compatible'` (RFC 5545) and jiff `Disambiguation::Compatible`; `LocalResult` is chrono's old name for `MappedLocalTime`. The wasm caveat (chrono #1701: `Local` on wasm returns only `Single`) is documented as out-of-scope. Tests inject `TZ`.
- `date_add` documentation widens to "any `DurationUnit` spelling"; the caveat that sub-day units may not change a date-only result lands with the precision fix.
- Deserialization uses a manual `Deserialize` via the module's own parser (house precedent: the duration type's existing manual impl). `Serialize` is explicit interop and emits RFC3339 `…Z` via chrono `to_rfc3339_opts(SecondsFormat::AutoSi, use_z = true)` (closed 2026-10-05, §13 RPT-F3 option (a): `AutoSi` preserves exact decimals without truncation); human `Display` remains the everyday local-naive spelling. Thus explicit-offset input round-trips as an instant, while only naive user-authored input takes the local→UTC resolver path; `%+` is never used. Both errors get `#[non_exhaustive]`; exports made symmetric across the two domains (`DateTimeValue`/`DateError` exported alongside `DurationValue`/`DurationError`).
- Display rules: duration seconds render through a chosen dialect (exponent above a threshold), never raw `f64`; extreme/small synthesized values must not render as a lie (`"0s"` for nonzero).
- Invalid-pattern (`DelayedFormat`) rendering lives at exactly one site — the template-private `format_with` (`src/template/engine/date.rs:304`); we own no validator. **(Amended 2026-10-05, §11 X-A:** the original "one shared renderer … template vs core" wording presumed core `format_with` copies that ticket 03's remediation deleted — `grep "fn format_with" src/date.rs` → no match; the dedup was achieved by deletion, not by a shared `render_pattern`.**)**
- Moment→strftime translator is template-seam only, scope 1: bracket literals, `YYYY MM DD HH mm ss` family, `Do`/`S`, `dddd`/`ddd`/`MMM`/`MMMM`; everything else errors naming the token and dialect. The only strftime-grammar surface left is the engine's private `format_with` (template seam).
- `parse_with(text, fmt)` returns `Result` (one implementation serving the query `reference` case and future LSP needs).
- ISO-8601 duration strings (`P1M`, `P-1M`) are translated at the shorthand adapter, not added as a second grammar.
- **Format bindings:** core formatting stays a thin chrono wrapper; `chrono::format::strftime` is the documented grammar (intra-doc link in touched rustdoc); invalid-pattern detection is chrono's `DelayedFormat` error only — no parallel specifier validator; `%+` never emitted (chrono advises against it) — RFC3339 interop uses `to_rfc3339_opts(SecondsFormat::AutoSi, true)` to produce the `…Z` channel (RPT-F3 closed); format docs note `%Z` prints only an offset, `%S` may render `60` (leap second), and week numbers use `%V`/`%G` (ISO), not `%U`/`%W`.
- **Week mandate:** week bucketing/numbering delegates to chrono `NaiveDate::iso_week()` / `from_isoywd_opt` and weekday accessors; epoch-day division for weeks is forbidden (Dataview `.week` footgun).

**Dead surface & config (Decision C)**

- Wire or delete — **executed by ticket 03's remediation except the live `expect(dead_code)` census** (amended 2026-10-05, §11 X-B): `checked_add`/`checked_sub` superseded by the calendar owner's `apply` and **deleted**; `to_time_string`/`start_of_day`/`cmp_date` **deleted**; `to_offset_string` **deleted** — its `…Z` mandate is satisfied instead by `Serialize` (`to_rfc3339_opts(SecondsFormat::AutoSi, true)` at `src/date.rs`); core `format_with` **deleted** (template copy survives). The live `expect(dead_code)` set is six items: `DateValue::{shift, apply}`, `DateTimeValue::apply`, `DurationValue::{from_seconds, parts, is_calendar}` — all declared spec-mandated surface with declared consumers (04's `classify`, ticket 05). Deletion test re-run on `into_inner`/`From` chrono surface after the calendar owner landed confirms the need shrank (D7 honored).
- The config-module default-format constant is removed; callers substitute the crate's `DEFAULT_DATETIME_FORMAT` (value-neutral — the config const already holds that same datetime pattern despite its date-ish name; the misleading naming is noted in the commit/docs).

## Testing Decisions

- **A good test here exercises external behavior through a seam — never past it.** Tests assert contracts (trichotomy, bit-exact Σ, round-trip, equal-values-different-shifts, L→R apply order) not implementation lines; Arrange/Act/Assert kept visually separate; fresh per-test fixtures; time and `TZ` injected per test, never shared/global.
- **Seam 1 (primary) — value-type interfaces, in-module `#[cfg(test)]`:** parse/classify/shift/diff/format/serde for the date and duration types. Covers: panic→error (N1), signed-zero (`-0m`), `parts`/`fixed_seconds` invariants, the A2′ pinning test (and `1d` vs `24h` and `1w` vs `168h` shifting differently across DST with `1w` ≡ `7d` identical), bit-exact Σ (fold over signed `parts` in L→R order — `==`, for parsed values and `Some`+`Some` arithmetic results, both fold-based by construction; mixed-`None` arithmetic excluded from Σ, pinned structurally instead), multi-part `apply` written-order (`"1d 1h"` vs `"1h 1d"` across a DST boundary), non-finite `Mul` rejected by consuming conversions (`NonFiniteSeconds`, never panics), the D12 local-wall-clock clamp test (day/month shift across a DST transition keeps the local wall time; Jan 31 + 1 month → end-of-month clamp), DST earliest/gap tests with resolver gap-verification (error vs gap), `YYYY-MM` precision round-trip, serde's `…Z` interop round-trip while `Display` never emits `…Z`, error source chains, classify trichotomy asserted behaviorally (allocation itself is not observable through the seam), sign-rule pinning (N15b)**, and (added 2026-10-05, §13): f64→`TimeDelta` divergence pins `0.9999999996` and `-1e-10` through *both* entries (`seconds_delta` and `TryFrom<DurationSeconds>`); sub-second `DateTimeValue` serde round-trip (Serialize→Deserialize keeps the fraction); Display/Serialize of a *computed* duration (NU-1 drift — an arithmetic result's spelling is not a faithful encoding of its parts); accept-or-reject pin for space-separated fractional datetimes (`2026-07-29 14:30:00.123`, NU-2 — verify chrono's optional `%.f` first); leading-comma `raw` spelling (`",1h"`, NU-3 residue)**.
