## Findings

### A. Crate landscape and design philosophies

1. **chrono's self-description.** "Chrono aims to provide all functionality needed to do correct operations on dates and times in the proleptic Gregorian calendar." `DateTime` is "timezone-aware by default, with separate timezone-naive types"; "Operations that may produce an invalid or ambiguous date and time return `Option` or `MappedLocalTime`"; formatting is an "`strftime` inspired date and time formatting syntax". Timezone data "is not shipped with chrono by default" (use chrono-tz or tzfile). Limitations: proleptic Gregorian only, dates ±~262,000 years, nanosecond time, "Leap seconds can be represented, but Chrono does not fully support them". [source: https://raw.githubusercontent.com/chronotope/chrono/main/README.md]

2. **The `time` crate was extracted from the Rust source tree, not written fresh.** First crates.io release `0.0.1` published 2014-11-13 with `authors = ["The Rust Project Developers"]`; `time-rs/time`'s first issue/PR #1 (2014-11-11) states "This pull request was extracted from rust-lang/rust#18832", and that Rust PR (created 2014-11-10) renames `tm_gmtoff` → `tm_utcoff` in `time::Tm`, editing `src/libtime/lib.rs` and `src/rt/rust_builtin.c` in rust-lang/rust; `src/libtime/lib.rs` exists in rust-lang/rust at 2014 SHAs (raw fetch 200 at `262c1efe`) and is gone by tag `1.0.0`. The crate's own README contains no origin narrative. (The precise extraction direction is an inference from the above date/authorship/PR evidence, not a stated claim.) [source: crates.io `time` 0.0.1 .crate; https://github.com/time-rs/time/issues/1; https://github.com/rust-lang/rust/pull/18832]

3. **`time` is now a one-maintainer crate with rename churn.** Releases `0.2.0` (2019-12-19) and `0.3.0` (2021-07-30) were published by jhpratt (current docs.rs owner). CHANGELOG 0.3.54 (2026-07-20): "`PrimitiveDateTime` has been renamed to `PlainDateTime`", "`Duration` has been renamed to `SignedDuration`", with non-deprecated aliases kept for compatibility. [source: https://raw.githubusercontent.com/time-rs/time/main/CHANGELOG.md]

4. **jiff's positioning.** README: the focus is a "pit of success"; it "takes enormous inspiration from Temporal" (TC39); goal is an API "that makes it hard to do the wrong thing. Second to that is performance." [source: https://raw.githubusercontent.com/BurntSushi/jiff/master/README.md]

5. **jiff DESIGN.md's chrono critique (verbatim bullets).** "I found Chrono's API to be overengineered and difficult to deal with." … "Chrono has been steadily deprecating huge portions of its API in favor of fallible routines. I find the resulting documentation difficult to read and the naming to be very clunky." … "The fallible routines return a mixture of `Option<T>` and `Result<T, E>`. This is frustrating … because the `Option<T>` _usually_ needs to be converted to a human readable error message … Indeed, Jiff rarely returns `Option<T>` and instead returns `Result<T, E>` with a contextualized human readable error message." … "I find the use of generics in Chrono to be overengineered … making the notion of 'time zone' an open concept … rarely needed. The Chrono crate ecosystem makes use of this via the `chrono-tz` and `tzfile` crates, but Jiff covers both of those use cases … automatically." … "Chrono overall puts a large emphasis on 'fixed offset' datetimes, but these are rarely the right abstraction to use." … "I find generic traits like `Datelike` to also be very confusing because they split the APIs of types like `NaiveDate` into concrete methods and generic methods" … "Chrono's API doesn't offer clean on-ramps from civil ('naive') datetimes to time zone aware datetimes" (e.g. `NaiveDate::succ_opt` missing on `NaiveDateTime`/`DateTime`, vs `Zoned::tomorrow` in jiff) … "Chrono lacks a standard timestamp type." [source: https://raw.githubusercontent.com/BurntSushi/jiff/master/DESIGN.md, §Chrono]

6. **jiff DESIGN.md on `time`.** "My main gripe with the `time` crate is that it has very limited IANA Time Zone Database support. This means it is difficult to do DST safe arithmetic. Consequently, it emphasizes the use of 'fixed offset' datetimes in a similar fashion as Chrono, except `time` does not provide any extension mechanism like a `TimeZone` trait." [source: DESIGN.md, §`time`]

7. **jiff serializes zoned datetimes with an embedded IANA id (RFC 9557).** Example from DESIGN.md: `2024-07-21T17:11-04[America/New_York]`. [source: DESIGN.md]

### B. Ambiguous local time (gaps and folds)

8. **jiff's disambiguation strategy is an explicit, non-exhaustive, runtime-configurable enum.** `pub enum Disambiguation { Compatible, Earlier, Later, Reject }`, "The default value is `Disambiguation::Compatible`, which matches the behavior specified in RFC 5545 (iCalendar). Namely, when an ambiguous datetime is found in a fold (the clocks are rolled back), then the earlier time is selected. And when an ambiguous datetime is found in a gap (the clocks are skipped forward), then the later time is selected." `Earlier`/`Later` always pick that side; `Reject` "will always result in an error … if you need to require datetimes from users to unambiguously refer to a specific instant." The enum exists "to expose the disambiguation strategy as a runtime value for configuration purposes" (e.g. on `fmt::temporal::DateTimeParser`). Worked example: gap `2024-03-10T02:30[America/New_York]` → compatible resolves to `03:30 -04` (later), earlier resolves to `01:30 -05`. [source: https://docs.rs/jiff/latest/jiff/tz/enum.Disambiguation.html]

9. **chrono's ambiguity result is `MappedLocalTime` = `LocalResult`, and `None` conflates a DST gap with data/OS errors.** Source: `pub type MappedLocalTime<T> = LocalResult<T>;` with `pub enum LocalResult<T> { Single(T), Ambiguous(T, T), None }` documented as "Old name of MappedLocalTime". The `None` doc: it "may also be returned if there was an error while resolving the local time, caused by for example missing time zone data files, an error in an OS API, or overflow" — i.e. a nonexistent wall time and a resolution failure are the same value. [source: https://docs.rs/chrono/0.4.45/src/chrono/offset/mod.rs.html]

10. **chrono gives `Option`-returning accessors but no "shift forward" primitive for gaps.** `.single()` returns `Option<T>` and is `#[must_use]` (its `# Errors` section: returns `None` for fold and gap); `.earliest()`/`.latest()` return the earliest/latest of an ambiguous pair and `None` in a gap — so the RFC-5545 "later wall time after a gap" behaviour (our spec's shift-forward) must be hand-rolled. `.unwrap()` on the enum has a documented `# Panics` section. Note the README links `MappedLocalTime` to `…/offset/enum.MappedLocalTime.html`, which 404s; `type.MappedLocalTime.html` and `enum.LocalResult.html` both resolve (link rot / rename residue). [source: https://docs.rs/chrono/0.4.45/chrono/offset/enum.LocalResult.html; README]

11. **Our spec's disambiguation convention matches the RFC 5545 / Temporal / jiff default.** Spec: ambiguous → `.earliest()`, nonexistent → shift forward. jiff `Compatible`: fold → earlier time, gap → later (post-gap) time. Same semantics; jiff offers it as one named default, chrono requires combining `.earliest()` with manual gap handling (finding 10). [source: `.scratch/temporal-core/spec.md`; jiff Disambiguation docs]

### C. Duration model, equality, and serialization

12. **`std::time::Duration` is u64 seconds + u32 subsecond nanos with a paired panic/checked/saturating API.** Duration docs describe the `u64`/`u32` model, `MAX`/`ZERO` consts, and `from_*` constructors that panic on out-of-range/rounding overflow; the arithmetic ops come in trios (`checked_*` → `Option`, `saturating_*`, panicking operator). It deliberately has no `Display` (its `Debug` shows full precision). [source: https://doc.rust-lang.org/std/time/struct.Duration.html]

13. **chrono `TimeDelta` is a signed seconds+nanos complement with a canonical floor form.** "A `TimeDelta` is represented internally as a complement of seconds and nanoseconds. The range is restricted to that of `i64` milliseconds, with the minimum value notably being set to `-i64::MAX` rather than allowing the full range of `i64::MIN`. This is to allow easy flipping of sign, so that for instance `abs()` can be called without any checks." Private fields carry the invariant `nanos: i32, // Always 0 <= nanos < NANOS_PER_SEC`; constructors carry units (weeks/days/hours/… defined as fixed second counts — `SECS_PER_DAY = 86_400`). `Display` prints an ISO-8601-shaped string with total seconds (`{sign}P…T{secs}[.{frac}]S`; zero prints `P0D`). [source: https://docs.rs/chrono/0.4.45/src/chrono/time_delta.rs.html]

14. **chrono/std duration equality is magnitude identity by construction — the same convention our spec adopts.** `TimeDelta` derives `PartialEq, Eq, PartialOrd, Ord` over the normalized `(secs, nanos)` pair; every constructor/operation floors into `nanos ∈ [0, 1e9)` (`try_milliseconds` splits via `div_mod_floor_64`, `checked_add`/`checked_sub` carry across the second boundary), so `1h30m` and `90m` are the same value structurally. [source: time_delta.rs]

15. **chrono `TimeDelta` serde: a `(secs, nanos)` tuple, feature-gated, added 0.4.39 (2024-12-09, PR #1599).** Serialize: `serialize_struct`-free 2-tuple `<(i64, i32)>::serialize(&(self.secs, self.nanos), …)`; deserialize: `TimeDelta::new(secs, nanos).ok_or_else(|| Error::custom("TimeDelta out of bounds"))`. GitHub issue #117 "Add Serialize/Deserialize for Duration" is **still open** despite the impl shipping — tracker drift. [source: time_delta.rs; https://github.com/chronotope/chrono/releases/tag/v0.4.39; issue #117 checked 2026-09-25]

16. **serde's own `Duration`/`SystemTime` wire format is a named struct, format-agnostic.** `Duration` → `serialize_struct("Duration", 2)` with fields `secs` (`as_secs()`) and `nanos` (`subsec_nanos()`) — the same shape for JSON and binary (no human-readable branch). `SystemTime` → struct with `secs_since_epoch`/`nanos_since_epoch` and errors "SystemTime must be later than UNIX_EPOCH" for pre-epoch values. [source: https://docs.rs/crate/serde/latest/source/src/ser/impls.rs]

17. **`time` splits binary vs human-readable serde behind an explicitly opt-in feature, with a library-facing warning.** `serde-human-readable` "Allows serde representations to use a human-readable format. This is determined by the serializer, not the user. If this feature is not enabled or if the serializer requests a non-human-readable format, a format optimized for binary representation will be used. **Libraries should never enable this feature, as the decision of what format to use should be up to the user.**" [source: https://docs.rs/time/0.3.55/time/index.html]

18. **jiff refuses blanket equality on its field-bearing duration (`Span`) and makes the choice explicit.** `Span` has no `PartialEq`; only `PartialEq<SpanFieldwise>` plus a `compare` method. COMPARE.md shows the consequence: `&zdt2 - &zdt1` equals `23.hours().fieldwise()` across a DST fold while `zdt1.until((Unit::Day, &zdt2))` equals `1.day().fieldwise()` — "the span of time is 23 hours … But if you ask for the span in units of days, you get exactly 1". So jiff distinguishes elapsed-time identity from field identity instead of picking one. [source: https://docs.rs/jiff/latest/jiff/struct.Span.html; COMPARE.md]

19. **jiff serializes `Span` as an ISO-8601-shaped string and round-trips it fieldwise.** `5.years().months(2).days(1).hours(20)` → `"P5Y2M1DT20H"`; `assert_eq!(got, span.fieldwise())`. [source: COMPARE.md §"Jiff losslessly roundtrips durations"]

20. **humantime is the ecosystem's human-readable duration codec, with an explicit round-trip guarantee.** `format_duration(Duration::new(9420, 0)) == "2h 37m"`, `format_duration(Duration::new(0, 32_000_000)) == "32ms"`; doc: "this format is guaranteed to have same value when using `parse_duration`, but we can change some details of the exact composition of the value." Parsing accepts forms like `"2h 37min"` → 9420s. Adoption: 385 reverse dependencies of `humantime-serde`, including `trunk`, `iroh-gossip`, `nextest-runner`, the `tor`/`arti` family (`tor-config`, `arti-client`, …), `apollo-router`, `git-cliff-core`, `cargo-tarpaulin` (crates.io reverse-dependency API, 2026-09-25). [source: https://docs.rs/humantime/2.3.0/humantime/fn.format_duration.html; crates.io API]

21. **`chrono-humanize` is the precedent for "duration → prose" output.** `HumanTime` is a "Duration wrapper that helps expressing the duration in human languages", with `to_text_en(self, accuracy: Accuracy, tense: Tense) -> String`, and `From<DateTime<TZ>>`/`From<Duration>`/`From<SystemTime>` conversions. [source: https://docs.rs/chrono-humanize/0.2.3/chrono_humanize/struct.HumanTime.html]

### D. Arrow / DataFusion storage and query semantics

22. **Arrow's `Timestamp` separates physical instant from display zone, and "unknown zone" is a distinct state from UTC.** Schema.fbs: 64-bit signed epoch, units `SECOND|MILLISECOND|MICROSECOND|NANOSECOND`, optional `timezone` string; the epoch is measured at `1970-01-01T00:00:00Z` **regardless of the timezone field** (the zone is display/annotation only), values are comparable only when the zones are known/equal; an *empty* timezone means "unknown timezone" in which the values are "wall clock time" and "must not be considered physical points in time". [source: https://github.com/apache/arrow/blob/main/format/Schema.fbs]

23. **Arrow splits absolute time from calendar time: `Duration` vs `Interval`.** `Duration` is "An absolute length of time unrelated to any calendar artifacts", 8-byte integer, unit defaults to `MILLISECOND`, and "adding/subtracting two durations should be a naive operation" (no calendar). `Interval` carries calendar units (`YEAR_MONTH`, `DAY_TIME`, `MONTH_DAY_NANO`) whose lengths "can differ in length during DST transitions". [source: Schema.fbs]

24. **Columnar validity: 1 = valid, 0 = null, and a missing bitmap is legal.** Spec: "Validity bitmaps are optional… arrays with a `null_count` of `0` may not have a validity bitmap"; consumers "must handle" absent bitmaps; `is_valid[j] -> bitmap[j / 8] & (1 << (j % 8))`; bitmaps start "all unset" (all null) at allocation; nested types each carry their own top-level validity bitmap. [source: https://github.com/apache/arrow/blob/main/docs/source/format/Columnar.rst]

25. **Timestamps are a parametric type requiring unit + timezone, and calendar metadata rides alongside.** Columnar spec (line ~124) lists `Timestamp` as needing `unit` and `timezone` parameters; a `trading-time` timestamp example carries "market trading calendar" metadata — precedent for attaching semantic calendars to otherwise-plain instants. [source: Columnar spec]

26. **DataFusion `date_trunc` is strict and self-describing at the seam.** Granularity parse is case-insensitive (`match s.to_lowercase().as_str()`) over `microsecond…year`; on miss: `exec_err!("Unsupported date_trunc granularity: '{s}'. Supported values are: {supported}")` where `supported` is the joined allow-list; function alias `datetrunc`. [source: https://docs.rs/crate/datafusion-functions/55.1.0/source/src/datetime/date_trunc.rs]

27. **DataFusion's ISO week truncation is Monday-based (two independent implementations).** Calendar path: `d - TimeDelta::try_seconds(60 * 60 * 24 * d.weekday() as i64)` (chrono weekday counts Monday = 0); fast path: `nanos_from_days(days - (days + 3).rem_euclid(7))` with comment "num_days_from_monday for the epoch (a Thursday) is 3". Matches our spec's "ISO Monday weeks". [source: date_trunc.rs]

28. **DataFusion patches DST gaps in local truncation with an ad-hoc 3-hour shift.** After `truncated.and_local_timezone(value.timezone())`, `LocalResult::None` is handled: "This can happen if the date_trunc operation moves the time into an hour that doesn't exist due to daylight savings. On known example where this can happen is with historic dates in the America/Sao_Paulo time zone. To account for this adjust the time by a few hours, convert to local time, and then adjust the time back" — implemented as subtract 3 hours, re-attach tz, add 3 hours. `LocalResult::Ambiguous` picks a side with its own comment. [source: date_trunc.rs]

29. **DataFusion `date_part` is strict, case-normalized, and documents Postgres deviations.** Two sites return `exec_err!("Date part '{part}' not supported")`, plus `not_impl_err!("Date part {unit:?} not supported")` for intervals; comments record "century and decade are not supported by `DatePart`, although they are supported in postgres", "Postgres `isodow` is 1..=7 with Mon=1", "Month-to-second conversion uses 30 days as an approximation. This matches PostgreSQL's behavior for interval epoch extraction", and a deliberate string→timestamp implicit cast that is "Not consistent with Postgres and DuckDB but to avoid regression". [source: https://docs.rs/crate/datafusion-functions/55.1.0/source/src/datetime/date_part.rs]

30. **DataFusion `to_char` standardizes on chrono's strftime dialect.** Its user docs describe the pattern as "based on a Chrono format" linking to `chrono::format::strftime` docs, and the implementation imports `chrono::{NaiveDateTime, Timelike}` — in the Rust data stack, chrono's specifier table is the de facto dialect. [source: https://docs.rs/crate/datafusion-functions/55.1.0/source/src/datetime/to_char.rs]

31. **There is no `age` function anywhere in `datafusion-functions` 55.1.0.** The `functions()` lists of every scalar package were enumerated — `core`, `datetime` (`current_date, current_time, date_bin, date_part, date_trunc, default, from_unixtime, make_date, make_time, to_char, to_date, to_local_time, to_time, to_unixtime`), `math`, `string`, `unicode`, `regex`, `crypto` (`digest, md5, sha224, sha256, sha384, sha512`), `encoding` (`encode, decode`), `nested` — no `age` in any. (Best-effort: enumeraated from package `mod.rs` sources; string-literal greps for `age` also came back empty. PostgreSQL has `age()`, so our implementation would have no Rust in-ecosystem precedent.) [source: docs.rs source browser, datafusion-functions 55.1.0]

### E. Formatting and strftime

32. **chrono owns a full strftime dialect with documented year bounds.** `chrono::format::strftime` docs carry a specifier table (`%Y %C %y %q %m %b %B %h %d %e %a %A %w %u %U %W %G %g %V %j %D %x %F %v %H …`) and note valid years −262144..262143, with a sign required for years outside 0000..9999. [source: https://docs.rs/chrono/latest/chrono/format/strftime/index.html]

33. **`time` ingests strftime patterns as format descriptions.** `time::format_description::parse_strftime_borrowed` / `parse_strftime_owned`: "Parse a sequence of items from the strftime format description." [source: https://docs.rs/time/0.3.55/time/format_description/index.html]

34. **jiff ships a printf-style `fmt::strtime` module with `strftime`/`strptime` methods** (`civil::Date::strftime`, `Zoned::strptime`); `https://docs.rs/jiff/0.2.37/jiff/fmt/strtime/index.html` resolves (200) while the older `/fmt/strftime/` path 404s. [source: docs.rs URL checks]

35. **No shared standard Rust strftime implementation exists.** crates.io has no `strftime` crate (API 404); the nearby options are niche: `libc-strftime` (wraps glibc), `strftime-rs` (a tzcode `strftime.c` port, negligible downloads), `time-format`. Each datetime crate implements its own dialect (chrono §32, time §33, jiff §34), and DataFusion documents its format against chrono's (§30). [source: https://crates.io/api/v1/crates/strftime]

### F. Error-vs-panic doctrine

36. **std establishes the triad and the must-use idiom.** Panicking ops are paired with `checked_*` (`Option`) and `saturating_*` variants; `#[must_use]` applies "on types, impls, and traits, on functions, and on methods" with an optional message, backed by the warn-by-default `unused_must_use` lint. [source: https://doc.rust-lang.org/std/attribute.must_use.html]

37. **chrono documents panics rather than banning them, and twins every panicking constructor.** `TimeDelta::seconds`-style constructors carry `# Panics` sections ("Panics when the duration is out of bounds") beside `try_seconds` → `Option` with `# Errors` sections; `LocalResult::unwrap` likewise documents its panic; `.single()` is `#[must_use]`. [source: time_delta.rs; LocalResult docs]

38. **jiff's stated doctrine is `Result` with a contextualized human-readable message, not `Option`.** See finding 5 (DESIGN.md quote): "Jiff rarely returns `Option<T>` and instead returns `Result<T, E>` with a contextualized human readable error message." [source: DESIGN.md]

39. **DataFusion's doctrine is a strict error at the public seam that names the allow-list.** `exec_err!("Unsupported date_trunc granularity: '{s}'. Supported values are: {supported}")`, `exec_err!("Date part '{part}' not supported")` — errors are actionable rather than silent coercion (findings 26, 29). [source: date_trunc.rs, date_part.rs]

### G. Null and ordering semantics

40. **Rust std gives null a rank: "`None` always compares less than any `Some`."** Verbatim doc comment on `PartialOrd for Option<T>`; the match arms return `Ordering::Less` for `(None, Some(_))`. Linked from the std docs section "comparison operators". [source: https://raw.githubusercontent.com/rust-lang/rust/master/library/core/src/option.rs]

41. **SQL (PostgreSQL) gives null no rank: "Ordinary comparison operators yield null (signifying 'unknown'), not true or false, when either input is null. For example, `7 = NULL` yields null, as does `7 <> NULL`."** Our spec's "null never satisfies ordering" follows this SQL semantics, and is a deliberate divergence from Rust's `Option` ordering (finding 40). [source: https://www.postgresql.org/docs/current/functions-comparison.html]

42. **Arrow carries nulls out-of-band in validity bitmaps (finding 24), and physical-point comparability depends on known zones (finding 22)** — i.e. both precedents push "null/rankless" and "unzoned/unorderable" out of the value type and into metadata/state checks, which is the same shape as our null-never-orders and naive-vs-zoned rules.

### H. Security, dependencies, and conventions

43. **Both major temporal crates shipped a localtime-related segfault CVE in the same campaign.** RUSTSEC-2020-0071: "Potential segfault in the time crate", issued 2020-11-18, aliases CVE-2020-26235 / GHSA-wcg3-cvx6-7396, CVSS 6.2, "Patched >=0.2.23", reference `time-rs/time#293`. RUSTSEC-2020-0159: "Potential segfault in `localtime_r` invocations" (chrono), issued 2021-10-18, related CVE-2020-26235, "Patched >=0.4.20", reference `chronotope/chrono#499`. [source: https://rustsec.org/advisories/RUSTSEC-2020-0071.html, .../RUSTSEC-2020-0159.html]

44. **The Arrow Rust stack is chrono-based.** `arrow-array` 60.0.0 depends on `chrono = "0.4.40"` with `features = ["clock"]` and optional `chrono-tz = "0.10"` — no jiff/time presence; interoperability with the DataFusion/Arrow world means speaking chrono (or converting at the boundary). [source: https://docs.rs/crate/arrow-array/60.0.0/source/Cargo.toml]

45. **`time` gates system-UTC-offset access behind an explicit feature.** `local-offset` "(implicitly enables std) This feature enables a number of methods that allow obtaining the system's UTC offset" — offset access is opt-in rather than ambient, and `time` bundles no IANA database (no tz-db feature exists in the feature list). (Unverified: the per-platform caveat list in `LocalOffset`'s docs was not re-fetched this pass.) [source: https://docs.rs/time/0.3.55/time/index.html]

46. **Visibility narrowing idioms for a layered temporal core.** Rust Reference: items are private by default; `pub(in path)` restricts to a module path, `pub(super)` to the parent, `pub(crate)` to the crate — the sanctioned way to keep normalization helpers and zone-resolution internals out of the public API without a second crate. [source: https://doc.rust-lang.org/reference/visibility-and-privacy.html]

## Rust idioms worth adopting or citing

- **Triad arithmetic: panicking op + `checked_*` + `saturating_*`** (findings 12, 36) — our duration math should expose all three, with `# Panics` documented (finding 37).
- **`#[must_use]` on every resolution/parse entry point** (findings 10, 37) — cheap, warn-by-default guard against dropped ambiguity/null results (findings 36).
- **Strict seam errors that print the allow-list** (findings 26, 39) — copy the `Supported values are: …` pattern for `age`, `date_part`, `date_trunc`-style inputs.
- **`Result` with a contextualized human-readable message over `Option`** (findings 5, 38) — matches our "strict errors at public seams" rule and is the strongest single critique of the chrono-era pattern.
- **Canonical normalization → magnitude-identity equality** (findings 13, 14) — direct precedent for our "`1h 30m` == `90m`" rule; cite `TimeDelta`'s `0 <= nanos < NANOS_PER_SEC` invariant as the mechanism. jiff's `fieldwise` split (finding 18) is the alternative to cite if we ever need field-bearing durations.
- **Human-readable duration strings with a documented round-trip guarantee** (finding 20) — copy humantime's contract line ("guaranteed to have same value when using parse_duration") for our durationformat.
- **Named, non-exhaustive, runtime-configurable strategy enums** (finding 8) — `Disambiguation`-style `#[non_exhaustive]` enum with a `Default` for gap/fold policy keeps the policy swappable without API breaks.
- **Two-state serde: compact by default, human-readable only when the app opts in** (findings 16, 17) — serde's own format-agnostic `Duration {secs, nanos}` struct plus `time`'s "libraries must never enable the human-readable feature" warning is the right split for a library.
- **Absolute `Duration` vs calendar `Interval` as separate types** (finding 23) — Arrow's split mirrors our magnitude-identity durations vs calendar units; cite Schema.fbs for "unrelated to any calendar artifacts".
- **ISO-8601-shaped string serde for calendar spans** (finding 19) — `P5Y2M1DT20H` precedent for our durationformat serialized form.
- **Zone = annotation on a UTC epoch; empty/absent zone is its own state, not UTC** (findings 22, 42) — cite Schema.fbs for "wall clock time" vs physical point.
- **Validity metadata may be omitted when null_count = 0; consumers must tolerate absence** (finding 24) — if our storage layer copies Arrow conventions.
- **Attach calendars as metadata on timestamps** (finding 25) — the `trading-time` precedent for our precision/semantic layering.
- **Postgres-compat annotations on every deliberate deviation** (finding 29) — DataFusion's in-source comments ("This matches PostgreSQL's behavior…", "Not consistent with Postgres and DuckDB but…") are a good documentation pattern for our Dataview-parity decisions.
- **chrono's strftime dialect as the interop target** (findings 30, 32) — if our "core dialect" must be recognizable to the Rust data stack, table it against chrono's specifier docs.
- **`pub(crate)`/`pub(super)` to seal internals** (finding 46) rather than splitting a second crate.
- **Humanized duration output shaped like `chrono-humanize`** (finding 21) — `Accuracy`/`Tense`-style knobs if we add prose rendering later.

## Warnings / known critiques of chrono-era design

- **Overengineering and API churn**: "overengineered and difficult to deal with"; "steadily deprecating huge portions of its API in favor of fallible routines" (finding 5). Concrete churn: `TimeDelta` panicking constructors were deprecated (2024-02-19) and the deprecation reverted (2024-03-26) — both visible in `src/time_delta.rs` git history. [source: GitHub commits for `src/time_delta.rs`]
- **The `Option`/`Result` mixture is the core ergonomic failure**: fallible routines "return a mixture of `Option<T>` and `Result<T, E>`", forcing callers to invent messages where the library had context (finding 5).
- **Trait-split APIs (`Datelike` etc.) and missing civil→zoned on-ramps** make operations inconsistent across `NaiveDate`/`NaiveDateTime`/`DateTime` (finding 5).
- **No standard timestamp type and heavy fixed-offset emphasis** in chrono (and even more so in `time`, which has no `TimeZone` extension point at all) (findings 5, 6).
- **Zone identity is lost on serde round-trip**: COMPARE.md's runnable example — "Chrono only serializes the offset, which makes lossless deserialization impossible. Chrono loses the time zone information" — deserializes to `DateTime<FixedOffset>` which then computes `02:00:59 -05:00` where the zoned value should be `03:00:59 -04:00`, i.e. silently wrong arithmetic after a round-trip. [source: COMPARE.md]
- **Absolute durations lie across DST**: "since `TimeDelta` assumes all days are exactly 24 hours long, you get a result of `0` days" for a day containing a gap — `delta.num_days()` collapses a real day (COMPARE.md example). Our magnitude-identity durations must not be used for day-granularity calendar claims. [source: COMPARE.md]
- **`MappedLocalTime::None` conflates "nonexistent local time" with "tz data/OS error"** (finding 9) — callers cannot distinguish user-facing DST behavior from infrastructure failure.
- **`localtime_r`-family segfaults hit both leading crates** (finding 43); offset/local-time acquisition should be isolated and failure-tolerant (see also `time`'s opt-in `local-offset`, finding 45).
- **`time` rename churn and feature footguns**: `Duration`→`SignedDuration`, `PrimitiveDateTime`→`PlainDateTime` in 0.3.54 (finding 3) plus the "Libraries should never enable this feature" serde warning (finding 17) — dependency-upgrade and feature-composition hazards for downstream libs.
- **Stale documentation/trackers**: chrono's README links `enum.MappedLocalTime.html` (404, finding 10); jiff COMPARE.md still claims "Chrono does not currently have Serde support for its duration type" (issue #117) although the impl shipped in 0.4.39 (finding 15) — third-party comparison docs drift; re-verify before citing.
- **Local-time truncation needs an explicit gap policy**: DataFusion's 3-hour shift workaround (finding 28) shows that even mature engines hand-patch DST gaps; our date/time arithmetic should resolve gaps by policy (shift forward, finding 11) rather than by repair-after-fact.
- **No shared strftime implementation** (finding 35): specifier behavior (week bases, `%V`/`%G`, year bounds) will drift between engines unless our core dialect pins its own table — cite chrono's (finding 32) as the nearest thing to a Rust consensus.
- **Comparability requires known zones**: Arrow refuses to treat unknown-zone timestamps as physical points (finding 22); mirror that in any ordering claim over unzoned values.
